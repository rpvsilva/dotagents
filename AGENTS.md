# dotagents

Rui's personal AI setup, written once and linked into every AI coding tool (Claude Code, Codex, Cursor, ...). The goal: one **portable** source of truth for instructions, skills, MCP servers and hooks, so switching tools or machines costs nothing.

This file governs work **on this repo**. `global/AGENTS.md` is a different thing: the personal instructions that `install.sh` links into every tool's global config.

## Principles

- **Portable first.** A skill says *what* to do, never which tool does it: "start one subagent per unit, each in its own worktree", not a specific tool call. Give a fallback when a capability may be missing ("if your harness has no subagents, work the units one by one"). Tool-only frontmatter (e.g. Claude's `disable-model-invocation`) is fine: other tools ignore it.
- **Adapters hold the rest.** Behaviour only one tool supports (subagent definitions, hook wiring, plugin manifests) lives in `adapters/<tool>/`, never inside a skill.
- **Hook logic is a script.** It lives in `scripts/hooks/`; each adapter only wires it up, so any tool with hooks reuses the same script.
- **Repo knowledge stays in its repo.** A skill reads per-repo notes from `.agents/<skill>-notes.md` in the target repo; nothing about a specific project lives here.
- **No secrets.** Keys and tokens come from env vars or untracked local files (`.gitignore` covers `*.local.*`, `.env*`, `secrets/`).

Write every skill and instruction file following the `writing-for-agents` skill when it is available.

## Contributing

`README.md` is the map for a newcomer: it names every skill (a row in its group, linking its `SKILL.md`), hook, subagent, MCP server, Claude plugin, mod and group, and links every `docs/` page. Add the entry in the same change as the thing; `tests/repo.test.sh` fails on a missing one.

### Add or change a skill

1. Create `skills/<name>/SKILL.md` (frontmatter `name` matching the folder, plus `description`). Supporting files sit beside it and are reached by relative links. Steps several skills share (learning the repo's rules, starting subagents) live once in `skills/_shared/conventions.md`; link to its section instead of restating it. Folders starting with `_` hold shared files, not skills.
   Every value the skill acts on that has a default (how many at once, which tracker) is a **Setting** (`GLOSSARY.md`): declare it in `skills/<name>/settings.json` (`kind`, `default`, `meaning`; see `scripts/settings.sh`) and have the skill read it through `~/.agents/bin/settings`, never from a notes file. A key in `skills/_shared/settings.json` is shared: a skill that reads it opts in with `{"shared": true}`, never redeclares it. Notes files hold Lessons only.
2. Write `skills/<name>/needs.json` (see **Parts, groups and needs** below): its `group`, every other part it links to, calls or starts as a need marked `required` or `optional`, and the subagents whose briefs it holds under `agents`.
3. Re-read it against the **portable first** principle: every tool-specific word replaced or given a fallback.
4. Run `./install.sh` and confirm `~/.agents/skills/<name>` and `~/.claude/skills/<name>` are links into this repo.
5. Add a row to the right group of the Skills table in `README.md`, linking its `SKILL.md`.

Done when the skill loads in Claude Code by name and the README row exists.

### Parts, groups and needs

Every skill, subagent, mod, hook and folder part (`remote`, `mcp`, `global`) is a **Part** in one **Group** (`GLOSSARY.md`), so a feature can be installed alone. The groups are named once, in `groups.json`; a new group gets a line there and a row in `README.md`'s Groups table. A part names its group and its needs in a `needs.json` beside it: `{"group": "<group>", "needs": {"<part>": "required" | "optional"}}`, plus `"agents": ["<subagent>", ...]` in a skill that holds briefs, and `"remote": ["<subagent>", ...]`, those of its `agents` that may run on the remote backend (`skills/remote-subagents/SKILL.md` says which uses that covers; no other skill says "remote-capable"). `scripts/parts.sh` reads them (`list`, `needs`, `closure`, `files`). `install.sh [tool] <group>|<part>...` installs only those parts, core and their required needs (an optional need only when named too), and installs add up; `uninstall.sh [tool] <group>|<part>...` removes them, keeping what another installed part requires. No word installs every part.

- A need is `required` when the part calls it and cannot work without it, `optional` when it works without it (e.g. falls back to local runs when remote is off). Declare every other part it links to (a relative link into `skills/<skill>/` or to any file or folder another part ships, as `scripts/parts.sh files` lists them), calls (`~/.agents/skills/<x>`, `~/.agents/bin/remote-agent`, `.agents/hooks/<x>`) or starts by name (a subagent in backticks); `tests/repo.test.sh` fails on an undeclared one.
- **Core** is never declared: `skills/_shared`, the `configure` skill, `~/.agents/bin/settings` and the hooks library (`scripts/hooks/lib.sh`, `secret-patterns.txt`) come with every group; `scripts/parts.sh files _shared` lists those files, and `tests/repo.test.sh` fails on a core part named as a need.
- A part's need on its own subagents, or a subagent's on its own skill, is implicit.
- No part or group is named `all`, `shared`, `claude`, `codex` or `cursor`: `install.sh` reserves those words.

### Add a subagent

1. Write its instructions as a portable brief next to the skill that starts it: `skills/<skill>/<name>-brief.md` or similar. The skill tells the subagent to follow that file and says what to use when no matching agent exists.
2. For each tool with agent definitions, add a thin wrapper in `adapters/<tool>/agents/`: frontmatter for that tool (model, tools, isolation) and a body that only points at `~/.agents/skills/<skill>/<file>`. Never copy the brief into a wrapper.
3. Add its name to `agents` in the `needs.json` of the skill holding its brief; it has no `needs.json` of its own and belongs to that skill's group. Another skill that starts it by name lists it under `needs`.
4. Run `./install.sh` and confirm each wrapper is linked into the tool's agents folder.

### Wire up a tool

1. Put tool-only files in `adapters/<tool>/` with a short `README.md` saying where they get linked.
2. Add an `install_<tool>` function and a `case` entry in `install.sh`, linking through the `link` helper so existing files get backed up to `~/.dotagents-backup/`.
3. Run `bash -n install.sh`, then `./install.sh <tool>` twice: the second run must change nothing but re-create links.

### Add a hook, Claude plugin, Claude mod or MCP server

- **Hook**: the script in `scripts/hooks/<name>.sh`, then the wiring per tool in `adapters/<tool>/hooks/`, calling it as `$HOME/.agents/hooks/<name>.sh` (`install.sh` fills that folder with one link per file: `lib.sh` and `secret-patterns.txt` always, each installed hook's script). `install.sh` merges each snippet into the tool's config with `scripts/merge-json.sh`, keeping what is already there. Declare its group and needs in `scripts/hooks/<name>.needs.json`.
- **Claude plugin**: add a line to `adapters/claude/plugins.txt`; `install.sh claude` installs it. It belongs to the `global` part (`global/needs.json`, group `personal`), so it needs no declaration of its own.
- **Claude mod** (a Claude Code plugin of function hooks): a folder `adapters/claude/mods/<mod>/` holding `.claude-plugin/plugin.json` named `<mod>`, a name no skill uses. `install.sh claude` links it to `~/.claude/skills/<mod>`, where Claude Code loads it and reloads it on every save. Keep its logic in plain `.ts` files tested by `hooks/*.unit.ts` under `node --test`, and its `$` calls and drawing in the hooks module tested by `hooks/*.test.tsx` under `claude plugin test`; `tests/mod.test.sh` runs both. Declare its group and needs in `adapters/claude/mods/<mod>/needs.json`, beside `.claude-plugin/`, not under `hooks/`.
- **MCP server**: add it to `mcp/servers.json` with credentials as `${ENV_VAR}` references only, and the values in `~/.config/dotagents/mcp.env` (`KEY=value` lines, never committed). `install.sh` fills them in and installs the server for Claude Code (`claude mcp`), Codex (`~/.codex/config.toml`) and Cursor (`~/.cursor/mcp.json`); a server with an unset variable is skipped and named. Servers belong to the `mcp` part (`mcp/needs.json`), so a new one needs no declaration.

### Add an eval case

An eval case runs one skill's prompt in a throwaway home and checks what it leaves. It lives in `evals/<skill>/<case>/`: `case.json` (the full `model` ID and `caps`, plus optional fields), `prompt.md`, `fixture/` (the repo the run starts in, as plain files: no `.git`, no `test_*.py`), `checks/` (one executable per check), and optional `input/` and `rubric.md`. `docs/evals.md` holds the format. `evals/<skill>` must name a skill; folders `evals/_*` hold the runner. Evals are dev tooling, not a Part: no `needs.json`, and no part ships a file under `evals/`. They run on this machine only when you ask, never in CI. `python3 -I evals/_runner/cases.py check` checks every case.

### Pull requests

`agent-pr-gate` decides what a PR needs before it may merge; its rules are in `.review-gate.yml`.

- Fill in `Testing`, `Risk` and `How to revert` from `.github/pull_request_template.md`. Under `Testing`, write what you ran and its result; `TODO` or `N/A` counts as empty.
- Open, update and merge PRs as the `rpvsilva-agent` GitHub App, not as Rui, so Rui can approve them: prefix each `gh` call and `scripts/merge-pr.sh` with `GH_TOKEN="$(scripts/gh-app-token.sh)"`. Setup: the App ID in `~/.config/dotagents/github-app.env` (`DOTAGENTS_APP_ID=...`) and its private key at `~/.config/dotagents/github-app.pem`. If either is missing, stop and ask Rui; never fall back to his account.
- Never approve a PR. Approval is Rui's, and an agent approving with his login would fake it.
- A PR touching a **high-tier** path (`.review-gate.yml`, mirrored in `CODEOWNERS`) needs Rui's approval. To make a path high-tier, add it to both files.
- Merge only with `scripts/merge-pr.sh <number>`. It runs `agent-pr-gate check` (the gate's read-only CLI, pinned to the commit the gate workflow uses; needs `node`), which waits for CI and judges the PR by `.review-gate.yml`, and merges only when it passes, pinned to the head commit it judged. A PR into another branch (a `build-epic` ticket PR into an integration branch) merges without the gate: run `tests/run.sh` on it first (for a ticket PR, `ship_ticket.py` runs `map.md`'s Checks, `tests/run.sh` among them, on its head before merging). The PR the gate judges, and that needs Rui's approval on a high-tier path, is then the integration branch's own PR into `main`. CI and the gate run on PRs into `main` only, to save runners, and CI and the gate workflow skip a draft PR until it is marked ready for review, so mark a PR ready only once its head is final (every fix pushed): each push to a ready PR bills a full CI run. The gate workflow runs only when a PR becomes ready and on a review, and never waits for CI on a runner; `merge-pr.sh` judges CI itself. Every job has a `timeout-minutes`. CI runs Linux (`ci.yml`); macOS is `tests/run.sh` on your machine; Windows is not tested. Never merge with `gh pr merge` or the web UI, and never push to `main`: the repo is private on GitHub Free, so GitHub enforces nothing and this script is the only gate. The `guard-merge` hook (`scripts/hooks/guard-merge.sh`, wired for Claude Code, Codex and Cursor) blocks those commands.
- After opening or updating a PR, stay on it until it merges. Run `scripts/merge-pr.sh` once CI is green on a low or medium PR, which needs no approval; on a high PR, check its review every few minutes and run `scripts/merge-pr.sh` once Rui approves. Stop and tell Rui when he requests changes, the PR closes, or the gate refuses it.
