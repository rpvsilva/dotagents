# remote

Running subagents on a remote backend for compute only: a Kubernetes cluster, Docker on this machine, or a VM or PC over SSH. The laptop keeps the code, the git history and the orchestrating session; the backend gets what one subagent needs for one task and gives back a patch. It never touches a repo or GitHub, so it works for any project, including ones the machine's owners have no access to.

## Where the pieces live

- **The cluster side** is yours to run: the agent-sandbox controller and a SandboxTemplate with its warm pool, built on the runner image (the one the `docker` and `ssh` backends use too). The `context`, `namespace` and `pool` Settings point at it; `context` and `pool` have no default.
  The image must ship shellcheck at the version in [`scripts/shellcheck-version`](../scripts/shellcheck-version): implementers run `tests/run.sh` there, and it fails on any other version. Rebuild the image when the pin changes here.
- **This repo is the client**: [`scripts/remote-agent.sh`](../scripts/remote-agent.sh), driving one backend script from [`scripts/remote-backends/`](../scripts/remote-backends/).

## Use

```sh
~/.agents/bin/remote-agent [--attach PATH]... [--name TASK] [--agent AGENT] [--home DIR] [--model NAME] [--] "<brief>" [worktree]   # or @brief.md, or - for stdin
~/.agents/bin/remote-agent --help   # the usage on stdout, exit 0; any other --option before the brief: the usage on stderr, exit 1
```

`install.sh` links the command there, so skills reach it from any project. Skills use it through the [remote-subagents](../skills/remote-subagents/SKILL.md) skill: a remote-capable subagent (one the `remote` list in the `needs.json` beside its brief names) runs here whenever `remote.env` exists. `--attach` copies a file or folder from outside the worktree (a task, a spec) to `~/attached/<name>` in the sandbox, read-only. `--agent` names the subagent whose brief it runs (e.g. `epic-implementer`): the sandbox runs the harness on the model that agent's wrapper for the harness sets (`model:` in `adapters/claude/agents/<agent>.md`, `model =` in `adapters/codex/agents/<agent>.toml`), as a local run of it does, so both get the same model; an agent with no wrapper for the harness is refused. Without a model from the wrapper, `remote.model` runs, else the harness's default; `remote.models` renames the wrapper's or `remote.model`'s model ([Harnesses and model gateways](#harnesses-and-model-gateways)). `--model NAME` runs that model instead, as given (`[A-Za-z0-9._:/@+-]`, starting with a letter or digit), and wins over `--agent`'s. `--home DIR` ships the setup found under `DIR` (its `.claude` and `.agents` pieces and `.claude.json`) in place of `$HOME`'s, as `remote-agent-pack.sh <dir> DIR` stages it; a `DIR` that does not exist is refused before any backend call, and the Settings, the token and the backend's client still come from the real `$HOME` and `XDG_CONFIG_HOME`. `--name` names the task (e.g. a task's `TT-NN-<slug>`), made a valid label value (lowercase, `[a-z0-9-]`, at most 63 characters): every progress line on stderr starts with `[<task>]` (`[<run>]` without it), so several runs in parallel stay readable, and the backend labels the sandbox with it.

1. [`remote-agent-pack.sh`](../scripts/remote-agent-pack.sh) stages this machine's setup: `CLAUDE.md`, skills, agents, commands, rules, Codex's `~/.codex/{AGENTS.md,agents,prompts}` (never its `config.toml` or `auth.json`), `~/.agents/{skills,hooks}` (a skill in `~/.claude/skills` that is the same folder as its `~/.agents/skills` copy goes as a link to it; `~/.claude/skills/synced` and Python caches stay here), and this repo's [`capped`](../scripts/capped) as `~/.agents/bin/capped`; `settings.json` cut down to permissions, model, plugins and the hooks that call `~/.agents/hooks`; MCP servers that need no env or headers. Credentials, history, transcripts, caches and settings `env` never leave the machine; what it leaves out is printed.
2. It copies the attachments (minus secret-looking files) and lists the worktree's tracked and unignored files, minus secret-looking ones (the `guard-secrets` rule), and checks the size (`REMOTE_MAX_MB`, 200 by default).
3. It prints the path of the run's live transcript, `<common git dir>/remote-agent/<run>/transcript.jsonl`, then acquires a sandbox from the backend (on the cluster: claims a warm one) and puts the setup and the snapshot in as gzipped tar streams, saying how long each took (`claimed in <N>s`, `sent setup and snapshot in <N>s`, then `setup: <N> KB gzipped, sent in <N>s; snapshot sent in <N>s`; `run.json` keeps them as `send_setup_s`, `send_work_s` and `setup_kb`). On the cluster, the claim line names the pod's node. The credential goes through stdin, in a header of `NAME=value` lines (`REMOTE_HARNESS`, `REMOTE_BASE_URL` when set, the credential) ended by an empty line, before the brief.
4. In the sandbox, [`remote-agent-sandbox.sh`](../scripts/remote-agent-sandbox.sh) reinstalls the plugins and MCP servers (under `claude`), commits the snapshot as a base, and runs the harness headless on the brief (`claude -p`, or `codex exec --json`). Every shell command Claude runs (its Bash tool) goes through `capped` under the caps, passed as arguments after the sandbox script since the backends pass argv, not the environment: `remote.cap_mb` (`REMOTE_CAP_MB`; unset, `auto`) and `remote.cap_secs` (`REMOTE_CAP_SECS`, 300 s). The memory cap is the sandbox's share of its machine: its cgroup's memory limit (v2 `memory.max`, else v1 `memory.limit_in_bytes`) less 1024 MB for Claude (half a limit under 2048 MB), or 2000 MB when it has none; a `remote.cap_mb` only lowers it. The sandbox exports both as `CAPPED_MB` and `CAPPED_SECS`, so a test command's own `capped` with no flags runs under the same caps. The sandbox writes a small prefix script, `~/.agents/bin/capped-shell`, sets `CLAUDE_CODE_SHELL_PREFIX` to it after one probe through it, and says `== capped: shell prefix set (--mb N --secs N; sandbox limit: L MB)` (`none` with no limit); Claude Code runs the prefix with the whole command line as one argument, and the prefix caps only Bash-tool command lines (they end with `pwd -P >| <file>`), running hooks and MCP servers as they are. A command over a cap is killed (`capped: killed: memory` or `capped: killed: timeout` in its output), and Claude carries on: the kill is no failed run. Each kill goes to `~/out/capped.log` as `capped: killed: <kind> <command>` and, within a second, to stderr as `== capped: killed: <kind> <command>`, so it reaches `progress.log` even if the sandbox is lost after. Claude's text and tool calls are indented on stderr, so no line of theirs passes for a `==` line or a backend error. When the probe fails (no `capped`, no `python3` to run it, or neither `ps` nor `/proc`: on Linux `capped` reads the process groups from `/proc` when there is no `ps`), the sandbox logs `== capped: unavailable (missing: ...)`, naming what it lacks, and the run goes on uncapped; `result.json` says so in `capped_off`. The cap is per command, not for Claude nor the sum of commands run at once. Its progress shows on stderr, and in the sandbox's own log with every step of `remote-agent` (`kubectl logs <pod>`; `progress.log` in the sandbox's home where there is no such log). The token never goes there. Claude's raw `stream-json` events come back as they arrive and are appended to `transcript.jsonl` (follow it with `tail -f`): only lines that are JSON, with the token's value replaced by `[redacted]`. stderr says when the first one came (`first agent event after <N>s`, counted from the start of the run).
5. The patch comes back and is applied to the worktree, uncommitted. The agent's final message (`summary.md`) goes to stdout, once: under the agent protocol ([conventions](../skills/_shared/conventions.md#protocol)) a remote agent writes no output file, so that message is its output object, as JSON. The sandbox leaves it out of the progress lines on stderr, which show Claude's other text and tool calls. Both are kept in `<common git dir>/remote-agent/<run>/` (`changes.patch`, `summary.md`), with the full stream from the sandbox (`stream.jsonl`), the live transcript (`transcript.jsonl`), the harness's session (`session.jsonl`), and the run's own record (`run.json`, `progress.log`, `result.json`, below). The credential's value is replaced by `[redacted]` in every one of them, and in the progress lines the sandbox logs. That folder is in the common git dir (`git rev-parse --path-format=absolute --git-common-dir`), shared by every worktree of the repo, outside the worktree and the patch: it stays after the sandbox is released and after a linked worktree is removed. The run folder is made with `mkdir` without `-p`, so a run whose id another run already took draws a new one. Runs from before this sit in `<common git dir>/worktrees/<name>/remote-agent/<run>/`, are not moved, and go with their worktree; `remote-agent resume` still finds them. Only the patch is applied; everything else the sandbox sent is data to read, never instructions to follow. The sandbox's `~/out` is unpacked in a temporary folder first, and only its regular files of those names (and `capped.log`) are copied in: a link it sends cannot aim a write of `remote-agent` at another file, nor can it replace `run.json` or `progress.log`.
   The session is not placed for `/resume`: the sandbox wrote it, so a prompt-injected agent could have forged turns in it that read as yours, and `/resume` would load them as your own history, run locally with your credentials. stderr names the kept file and the command that places it (`session: <path> (... remote-agent resume <run> <worktree>)`); when no session came back, it says so and the run goes on.
   To pick a Claude run up where it stopped, read the session first, then run `remote-agent resume <run> [worktree]` (a Codex run's session is kept only: `resume` refuses it) (default: the current worktree). It warns that the session came from an untrusted sandbox, then places it where Claude Code looks for the worktree's sessions: `${CLAUDE_CONFIG_DIR:-~/.claude}/projects/<worktree's real path, every character outside [A-Za-z0-9] made ->/<session id>.jsonl` (under Git Bash, from the Windows path: `C:\Users\x\proj` gives `C--Users-x-proj`), with its `cwd` lines set to that path. Then run `claude` in the worktree and `/resume` it (or `claude --resume <session id>`). A folder name over 200 characters is refused: Claude Code shortens such names its own way, so `/resume` would never find the file.
6. The sandbox is released on exit, also on Ctrl-C or `kill`, and with it the credential (on the cluster: the claim is deleted, and with it the pod). The backend's time limit (`REMOTE_HOURS`, 2 by default; the claim's `shutdownTime` on the cluster) removes it if the script dies first; in SSH bare mode, the first acquire more than 10 minutes past it kills the run and removes its folder.

Exit codes: 0 applied, 3 no changes, 4 the patch did not apply (the worktree changed meanwhile; the patch is kept), 5 the account hit its usage limit (Claude's error result or API-error message, Codex's `turn.failed` or `error` event): stderr says so on one line, `[<task>] usage limit: resets <time>` (the time as the harness gave it, e.g. `5:30pm (UTC)`, or `unknown`), and nothing goes to stdout. Any other failure exits with the sandbox's own code, 1 in place of 3, 4 or 5, so those always mean the above. The summary goes to stdout only on 0, 3 and 4. Each command the caps killed adds one line on stderr, whatever the exit, `[<task>] killed: memory|timeout <command>`, matched from the `== capped: killed:` lines in `progress.log` (else from the `capped.log` that came back, kept beside it); a kill alone changes no exit code.

### What a run says about itself

From the moment its folder exists, every run keeps two files beside `transcript.jsonl`, and a third when it ends, so any reader (a Claude Code mod, `tail -f`, another tool) follows it from files instead of stderr:

- **`run.json`**: what the run is and where it stands. `run` (the folder's name), `name` (the `--name` as made a label value, else `null`), `worktree`, `harness` (`claude` or `codex`), `started` and `ended` (epoch seconds), `pid` and `pid_start` (`remote-agent`'s process and its `ps -o lstart=` in the C locale, as a reader's `LC_ALL=C ps` prints it), `state`, `exit_code`, `claim_s`, `send_s`, `first_event_s` (whole seconds; `null` until known), and `caller`, the Claude Code session that ran it, so a viewer such as a Claude Code mod shows a session its own runs: `session` and `claude_pid` from `CLAUDE_CODE_SESSION_ID` and `CLAUDE_PID`, which Claude Code gives every Bash command; each is `null` when unset, over 128 characters or not a plain id (`[A-Za-z0-9_.:-]`, and digits for `claude_pid`). `state` is `starting` when the folder is made, `running` just before the sandbox run starts, then `done` on exit 0 or 3 and `failed` on any other (1, 4, 130 on Ctrl-C, 143 on `kill`), `exit_code` saying which. Each write goes to a temporary file then `mv`, so it is valid JSON at every read; it never holds the brief or the token, and a failed write never fails the run. A `kill -9` (or a reboot) runs no exit step: `starting` or `running` with `pid` not alive, or alive with another `pid_start`, means the run stopped without saying so.
- **`result.json`**: what the run came to, written by [`remote-agent-result.sh`](../scripts/remote-agent-result.sh) on every exit, also a failed or interrupted one (not after `kill -9`). `run`, `name`, `exit_code`; `status` (`done` on exit 0 or 3, else `failed`, as `run.json`'s `state`); `report_status` (the `status` of the output object the final message holds, e.g. `done` or `blocked`; one code fence around the object is allowed; `null` when the message is no JSON object or has no string `status`); `changed` (the files `changes.patch` touches, `[]` when it is empty, `null` when no patch came back); `report_path` (`summary.md`, the agent's output; `null` when none came back); `duration_ms`, `num_turns`, `total_cost_usd` and `usage` (from the transcript's last `result` event; `duration_ms` from `run.json`'s times without one) `harness` (`run.json`'s, `claude` for an older run), `harness_version` and `model` and `claude_version` (the sandbox's Claude Code version), both from the transcript's `system`/`init` event. `complete` is `true` only on exit 0, 3 or 4 with a result event that is not an error. Anything unknown is `null`, never 0: a run that failed before Claude reported has `total_cost_usd: null`, while the usage-limit failure (exit 5) keeps the cost its error result shows. It is written through a temporary file then `mv`, with the token's value redacted, and a failed write never changes the exit code. A caller that lost stdout, stderr or `$?` reads the run's outcome here. `remote-agent result <name|run> [dir]` prints it without knowing the folder: for the run with that id, or the newest run (latest `run.json` `started`, then the `run.json` written last) whose `name` is `<name>` made a label value as `--name` makes it, among the repo's runs, old-location ones included, preferring runs whose `run.json` `worktree` is the caller's. One line on stderr and exit 1 when none matches, the argument is not a run or task name, or the newest match has no `result.json` yet (still running): never an older run's result in its place. Runs started at once, with stderr in a file or through `2>&1 | cat`, each keep their own folder, `progress.log` and `result.json`, so each is read right.
  It also holds `caps` (`{mb, secs}`: the caps the sandbox set, `null` when it set none), `capped_off` (`null`, or what the sandbox lacked to run the caps, e.g. `python3`: they were off and every command ran uncapped; the sandbox also says `== capped: unavailable (missing: ...)` on stderr), `capped_kills` (each command the caps killed, `[{kind, cmd}]`: `kind` `memory` or `timeout`, `cmd` `null` when the line names none; `[]` when none), `killed` (the last kill's kind, else `null`) and `lost` (`true` when the run failed with an exit other than 3, 4 or 5 and no kill line, and an error line of `remote-agent` or its backend's client (`kubectl`, `docker`) says its container or pod was gone: `No such container`, `container not found`, `pod "..." not found`). So a cap kill reads apart from a lost sandbox.
- **`progress.log`**: every progress line stderr shows, as it comes, without the `[<task>]` tag, the credential's value replaced by `[redacted]`. Its last line is the run's latest step.
- **Pruning**: `remote-agent prune --older-than <Nd|Nh> [--dry-run] [dir]` ([`remote-agent-prune.sh`](../scripts/remote-agent-prune.sh)) removes the run folders of the repo at `dir` (default the current one), in `<common git dir>/remote-agent/` and the old `<common git dir>/worktrees/<name>/remote-agent/`, older than N days (`d`) or hours (`h`), N at most 999999: by `run.json`'s `ended`, else `started`, else the folder's mtime. It never removes a live run: `starting` or `running` with `pid` alive and the same `pid_start` (where `ps` prints no start times, as in Git Bash, a `pid` alive is enough); one whose `pid` is gone or reused stopped, and goes. A folder whose name is no run name (`^[A-Za-z0-9][A-Za-z0-9._-]*$`) is left, with one line on stderr, and a link is neither followed nor removed. It prints `removed <path>` per folder, then `removed N runs`; `--dry-run` prints `would remove ...` and removes nothing. Any other age, or an unknown argument, is refused with the usage, exit 1. It does not touch copies a skill made elsewhere (build-epic's `<run>/remote/<task>.json`).

## Harnesses and model gateways

The harness is the agent CLI the sandbox runs on the brief, `remote.harness`: `claude` (Claude Code, the default) or `codex` (the Codex CLI). The runner image ships both, pinned in [`runner/Dockerfile`](runner/Dockerfile); the harness is picked per run, so `REMOTE_HARNESS=codex` in the environment switches one run.

| | `claude` | `codex` |
|---|---|---|
| Run | `claude -p <brief> --output-format stream-json`, the rules through `--append-system-prompt` | `codex exec --json --dangerously-bypass-approvals-and-sandbox -- <brief>`, the rules appended to `~/.codex/AGENTS.md` |
| Credentials (`remote.credential`) | `CLAUDE_CODE_OAUTH_TOKEN` (default), `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `GATEWAY_API_KEY` (given to Claude as `ANTHROPIC_AUTH_TOKEN`) | `CODEX_API_KEY` (default), `GATEWAY_API_KEY` |
| Gateway (`remote.base_url`) | exported as `ANTHROPIC_BASE_URL` | a `remote` model provider in `~/.codex/config.toml`: that `base_url`, `env_key` the credential's name, `wire_api = "responses"` |
| Gateway API (`remote.gateway_api`) | `anthropic` | `openai-responses` |
| Plugins and MCP servers | reinstalled from the packed setup | not installed |
| Caps (`capped`) | on, through `CLAUDE_CODE_SHELL_PREFIX` | off: Codex has no shell-prefix hook; `capped_off` says `a shell prefix in codex` |
| `result.json` | from the `result` and `init` events | turns and `usage` from `turn.completed`, `model` and `harness_version` from the session's `turn_context` and `session_meta`; no cost |
| `remote-agent resume` | places the session | refused; the session is kept |

`remote.credential` names the one Secret a run logs in with, from `remote.env` (else the environment); unset, it is the harness's default. A credential the harness does not take is refused before anything is sent. Only that one is sent, through stdin; its value is redacted in every kept file and in the progress lines the sandbox writes to its own log, wherever the agent echoes it. `remote.base_url` is a gateway, an `http` or `https` URL (no spaces or quotes), sent in the header and never as an argument. `remote.gateway_api` names the API it speaks; set, it must be one the harness speaks, else the run (and `check`) is refused before anything is sent; unset, the harness's own is assumed. `GATEWAY_API_KEY` is a gateway's key for either harness, so one LiteLLM key serves both; it, and `remote.gateway_api`, need `remote.base_url`. `setup`'s `gateway` login writes `GATEWAY_API_KEY`, the URL and the harness's API. Extra headers a gateway may want are not sent yet.

The model is `--model` as given, else the agent wrapper's for the harness, else `remote.model`, else the harness's default. `remote.models` (`name=model` entries, e.g. `opus=anthropic/claude-opus-5-5`) renames the wrapper's or `remote.model`'s model before the run, so wrappers keep the vendor's names while a gateway gets its own. A name may hold `/`, `:`, `@` and `+` for a gateway's naming.

## Backends

The `remote.backend` Setting names the backend; unset, remote runs are off and skills run subagents on this machine. Every remote Setting is declared, with its default and meaning, in [settings.json](settings.json), and lives at the machine Level (`~/.config/dotagents/settings.json`, through `~/.agents/bin/settings` or the `configure` skill); a repo can only set `remote.allowed` to `false`, which keeps its worktree snapshots on this machine, and `remote.open_pane` (true), whether Claude Code's `remote-runs` mod opens its pane when a run starts. `remote.max_sandboxes` (4) is how many remote subagents skills run at once, whatever the skill: set it to what the backend holds (the warm pool's size, the SSH host's cores; a claim on a full pool waits `REMOTE_CLAIM_TIMEOUT`, then fails). It is counted apart from a skill's `max_parallel`, which caps subagents on this machine; skills keep to it, `remote-agent` itself does not count runs. Each Setting's `REMOTE_*` variable, when set in the environment, overrides it for one run; the names below are those variables. Each backend is a script, `scripts/remote-backends/<name>.sh`. `remote-agent` exports every `REMOTE_*` setting to it (never the Claude token) and drives it with these operations only, so packing, secret filtering, the in-sandbox run, keeping results and exit codes stay the same on every backend:

| Operation | Does |
|---|---|
| `acquire <run>` | Gets a sandbox that removes itself after `REMOTE_HOURS`; prints its handle. |
| `put <run> <handle> <dir>` | Extracts the tar stream on stdin under the sandbox's `$HOME/<dir>`. |
| `run <run> <handle> <argv>...` | Runs the command in the sandbox with stdin, stdout and stderr streamed; returns its exit code. |
| `get <run> <handle> <dir>` | Writes a tar of the sandbox's `$HOME/<dir>` on stdout. |
| `release <run>` | Removes the sandbox, even after a half-done `acquire`; with `REMOTE_KEEP=1` keeps it and says what it kept. |
| `check` | Names, one line each, what this backend needs and is missing; fails when anything is. Used by `remote-agent check`. |
| `ping` | Probes the backend in a few seconds (cluster: `kubectl version --request-timeout=5s`; docker: `docker info`; SSH: a login with `ConnectTimeout=5`, then `docker info` on the host in container mode); on failure prints the error on one line and fails. Used by `remote-agent ready`. |

Shared helpers for backends live in `scripts/remote-backends/lib.sh`, which is not a backend.

### `cluster` (default)

An agent-sandbox SandboxClaim on a warm pool, driven with `kubectl exec`; the handle is the pod. Settings: `REMOTE_CONTEXT` (kube context) and `REMOTE_POOL` (warm pool; an agent listed in `remote.pools` claims from its own, see [One image per subagent](#one-image-per-subagent)), both required: unset, every step refuses with `REMOTE_CONTEXT not set` or `REMOTE_POOL not set`; `REMOTE_NAMESPACE` (`agents`), `REMOTE_HOURS` (the claim's `shutdownTime`, 2), `REMOTE_KEEP=1` (keep the claim: `kept sandboxclaim/<run>`), `REMOTE_CLAIM_TIMEOUT` (seconds to wait for the claim to be Ready, 180; on a timeout the claim's conditions are printed, and a claim the controller fails stops the run at once with its reason). The claim and its pod carry the labels `sandbox.users.io/remote-agent-run=<run>` and, with `--name`, `sandbox.users.io/remote-agent-task=<task>`: `kubectl get pods -L sandbox.users.io/remote-agent-task` tells the runs apart, and `kubectl logs -f <pod>` follows one. The labels sit under `sandbox.users.io` because agent-sandbox rejects pod labels outside its allowed domains (`AllowedLabelDomains`, default `sandbox.users.io`). Needs a kube context that can create SandboxClaims and exec into pods in the namespace.

### `docker`

A fresh container of the runner image on this machine for each run, driven with `docker exec`; the handle is the container, named after the run. It runs `sleep <REMOTE_HOURS*3600>` under `--rm`, so it removes itself after `REMOTE_HOURS` if `remote-agent` dies; otherwise `docker rm -f` removes it at the end, also on failure, Ctrl-C or `kill`. Like the cluster's pods, it carries the labels `sandbox.users.io/remote-agent-run=<run>` and, with `--name`, `sandbox.users.io/remote-agent-task=<task>`: `docker ps --filter label=sandbox.users.io/remote-agent-task` lists the named runs, and `docker logs -f <run>` follows one. Needs only Docker and the image. Settings, in `remote.env`:

- `REMOTE_BACKEND=docker`.
- `REMOTE_IMAGE`: the runner image, the `image` Setting's default, `ghcr.io/rpvsilva/agent-runner:main` (public: it pulls anonymously, with no `docker login`; for `linux/amd64` and `linux/arm64`; see [The runner image](#the-runner-image)), unless you set your own (`remote.image`). Empty, the backend refuses with `REMOTE_IMAGE not set`. A run of an agent listed in `remote.images` uses that agent's image instead: see [One image per subagent](#one-image-per-subagent).
- `REMOTE_PLATFORM`: passed to `docker run --platform` when set (e.g. `linux/amd64`); unset, Docker picks this machine's architecture.
- `REMOTE_HOURS` (2) and `REMOTE_KEEP=1` (keep the container: `kept container <run>`; it still removes itself after `REMOTE_HOURS`).
- `REMOTE_SANDBOX_MB` and `REMOTE_SANDBOX_CPUS` (`remote.sandbox_mb`, `remote.sandbox_cpus`): each run's share of the host, as `docker run --memory` (with `--memory-swap` the same: no swap past it) and `--cpus`. Unset, the host's memory and CPUs (`docker info`) over `REMOTE_MAX_SANDBOXES`, since other runs, and other people's, share it; `started container <run> (<image>; 4096 MB, 2 CPUs)` says what it got, and a share under 2048 MB adds a note. The sandbox caps its commands' memory under that limit.

**Apple Silicon** runs the default image natively: it is published for `linux/arm64` too. An image of your own published for amd64 only runs under emulation with `REMOTE_PLATFORM=linux/amd64`, but slowly.

The container gets Docker's default network: internet egress, and whatever this machine's network reaches. Anyone who can run `docker` here can see the snapshot and the token during a run.

### `ssh`

A VM or PC reached with `ssh`. In container mode (the default) it is the `docker` backend run on that host: a fresh container of the runner image per run, each `docker` command sent as one `ssh -T <login options> <host> '<command>'` call (see [Logging in](#logging-in)) with every word single-quoted, so any login shell (bash, zsh, dash) runs it as written. Files travel as tar streams through the connection, and the token through stdin: no `scp`, no temp files on either side, and the token never in `ssh` arguments. Containers are named after the run and labelled as for `docker`, so several runs can share the host; each is removed at the end, and `--rm` with its `sleep` removes it after `REMOTE_HOURS` if `remote-agent` dies. Settings, in `remote.env`:

- `REMOTE_BACKEND=ssh`.
- `REMOTE_SSH_HOST`: the ssh destination, `user@host` or an alias from `~/.ssh/config` (where a port, key or jump host go).
- `REMOTE_SSH_KEY`: a private key file to log in with, alone (`-i <file> -o IdentitiesOnly=yes`; a leading `~/` is this machine's home). Unset: the ssh agent's keys or `~/.ssh/config`'s.
- `REMOTE_SSH_MODE`: `container` (the default) or `bare` (see [Bare mode](#bare-mode-trusted-hosts-only)). Any other value stops the run, naming both.
- `REMOTE_SSH_SUDO` (`remote.ssh_sudo`, false): run every `docker` command on the host as `sudo -n docker`, for an SSH user outside the `docker` group who has passwordless sudo. Container mode only.
- `REMOTE_IMAGE`, `REMOTE_PLATFORM`, `REMOTE_HOURS` and `REMOTE_KEEP=1` as for [`docker`](#docker), applied on the host.

In container mode the host needs:

- **An SSH login** with a key or a password (see [Logging in](#logging-in)). `remote-agent check` tries it.
- **Docker** the SSH user may use: in the `docker` group (`sudo usermod -aG docker <user>`, then log in again), or through passwordless sudo with `remote.ssh_sudo` set to `true`. Either way the user can act as root on the host. When plain `docker` is refused but `sudo -n docker` works, `remote-agent check` says so and gives both fixes; sudo that asks for a password does not work, since nothing may wait on a prompt.
- **The image**: the default image is public and pulls with no login. For a private image, log in once on the host (`ssh -t <host> docker login ghcr.io`; with `remote.ssh_sudo`, `sudo docker login ghcr.io`, as root pulls) or build it there, and set `REMOTE_IMAGE` to its tag. Pick a `REMOTE_PLATFORM` or image that matches the host's architecture.

#### Logging in

Every call logs in on its own, in the background, so nothing may wait on a terminal. Two ways, both set by `remote-agent setup`:

- **A key**: from the ssh agent or `~/.ssh/config` (nothing to set), or a key file in `REMOTE_SSH_KEY`. An encrypted key file needs its passphrase in the agent (`ssh-add <file>`) or as the `SSH_KEY_PASSPHRASE` Secret.
- **A password**: the `SSH_PASSWORD` Secret.

The password and the passphrase are Secrets, in `~/.config/dotagents/remote.env` beside the harness's credential (mode 600), never Settings, never in `ssh` arguments, never sent to the host's commands. With neither set, every call runs with `-o BatchMode=yes`: no prompt at all. With either set, keys are still tried first, then one password try (`-o BatchMode=no -o NumberOfPasswordPrompts=1`), and ssh asks `scripts/remote-ssh-askpass.sh` (`SSH_ASKPASS` with `SSH_ASKPASS_REQUIRE=force`, OpenSSH 8.4 or later on this machine) instead of the terminal. It answers a password prompt with `SSH_PASSWORD` and a passphrase prompt with `SSH_KEY_PASSPHRASE`, and nothing else: an unknown host key's question gets no answer, so the login fails as with `BatchMode`. Add the host key first with one interactive `ssh <host> true`.

**Who can see the code and the credential during a run** in container mode: the host's root and every member of its `docker` group, since they can `docker exec` into the container or inspect it. Use a host only you (and people you trust with the credential) administer. The container gets Docker's default network on the host: internet egress, and whatever the host's network reaches.

#### Bare mode (trusted hosts only)

With `REMOTE_SSH_MODE=bare` the run happens directly on the host, as the SSH user, with no container. **This is weaker isolation**: the run shares the OS user with that user's own setup and with other runs, has no network limits beyond the host's own, and the SSH user (and the host's root) can read the code and the credential while a run lives. Prefer container mode whenever the host has Docker or is shared with anyone else.

- Each run gets its own folder, `$REMOTE_SSH_DIR/<run>` (mode 700), used as its `HOME`, with `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME`, Claude Code's config (`CLAUDE_CONFIG_DIR`) and Codex's (`CODEX_HOME`) inside it: the setup, plugins, MCP servers, token and files stay apart from the host user's `~/.claude` and from other runs. At the end, whatever still runs for the run is killed (by the pid and process group recorded in the folder's `.pid`; its own group via `setsid` where the host has it, else the process and its children via `pkill -P`), even a process that ignores `TERM`, then the folder is removed; `REMOTE_KEEP=1` still kills the run but keeps the folder (`kept run folder ...`) until an acquire removes it under the rule below. Only the run's own processes are signalled: a recorded pid counts as the run's only while its working folder is inside the run folder (read from `/proc`, else `lsof`), so a pid since reused by another process is left alone.
- The host needs the same SSH login as container mode, and no Docker.
- Before anything is sent, the host is checked for `bash`, `tar`, `git`, `jq`, `node` and `claude` on the SSH user's `PATH` (a `codex` run needs `codex` there too) (non-interactive login: set it in the shell's non-interactive startup file); each missing one is named and the run stops. Installers often put them where only an interactive shell looks (nvm's `~/.nvm`, Claude's `~/.local/bin`), which a command run over ssh does not see: link them into `/usr/local/bin` (`sudo ln -sf "$(command -v node)" /usr/local/bin/node`, the same for `claude`, from an interactive shell; redo the node link after switching versions with nvm). `remote-agent check` runs both with `--version`, so one that is found but does not start (Node from nvm on Ubuntu 24.04 needs `sudo apt-get install libatomic1`) is named with its error.
- A client that dies leaves its folder behind; the next run's acquire removes it, but never a live run. Each run records its own expiry in its folder's `.expires` (the host's clock plus that run's `REMOTE_HOURS`, set at acquire), and while it runs a host loop touches `.heartbeat` every 60 seconds. Acquire removes a folder when the host's clock is past its `.expires` and its `.heartbeat` is missing or older than 3 minutes, so another client's smaller `REMOTE_HOURS` cannot cut a run short. `REMOTE_HOURS` is still a hard limit: once the clock is more than 10 minutes past a folder's `.expires`, acquire removes it whatever its heartbeat, first killing what still runs there as release does, so a run whose client died and whose command never ends goes with the next acquire after that. A folder with no `.expires` (left by an older client) is removed when its mtime is older than the acquiring client's `REMOTE_HOURS`.
- The sandbox log is `progress.log` in the run folder (there is no container log), never the host's `/proc/1/fd/1`, even as root.
- Settings: `REMOTE_SSH_DIR`, the run folders' root on the host, absolute or relative to the SSH user's home (`.remote-agent/runs` by default); `REMOTE_HOURS` and `REMOTE_KEEP=1` as above. `REMOTE_IMAGE` and `REMOTE_PLATFORM` do not apply.

## Setup, once

```sh
~/.agents/bin/remote-agent setup   # asks for the backend, its Settings, the harness and its credential
~/.agents/bin/remote-agent check   # checks the backend's needs, then a dry run
~/.agents/bin/remote-agent ready   # whether skills send this repo's subagents to the backend, and if not, why
```

`ready` checks the Settings and the harness's credential, then probes the backend (its `ping`, a few seconds at most). It prints the backend's name and exits 0, or prints one line saying why not and exits 1: a missing Setting or credential (`no CODEX_API_KEY in ...`), `remote.allowed` false, or `<backend> backend not reachable: <the error>` (e.g. `cluster backend not reachable: context my-cluster: Unable to connect to the server: dial tcp ...: connect: no route to host`).

`setup` asks for the backend and its details (cluster: kube context, by default the saved one or else the current one, namespace and pool, with no default unless one is saved; SSH: host, login (a key, from the agent or a key file with an optional passphrase, or a password) and mode; Docker: nothing more; the runner image for Docker and SSH container mode), and writes them as Settings to `~/.config/dotagents/settings.json`, keeping those it does not ask about (`hours`, `keep`, ...). It then asks for the harness (`claude` or `codex`) and how it logs in: for `claude`, `oauth` (run `claude setup-token` in another terminal and paste the token), `api_key` (`ANTHROPIC_API_KEY`) or `gateway` (its URL, asked again until it is http or https, and its bearer token, `ANTHROPIC_AUTH_TOKEN`); for `codex`, `api_key` or `gateway` (its URL and `CODEX_API_KEY`). It writes `remote.harness`, `remote.credential` and `remote.base_url` (unset unless a gateway), reads the credential without echo and never prints it; enter keeps the one already there. The credential, the SSH password and the key passphrase are Secrets, read the same way, so they go alone to `~/.config/dotagents/remote.env`, readable only by you (mode 600); choosing one SSH login drops the other's Secret, while another harness's credential stays. A `remote.env` from before `settings.json` still holds `REMOTE_*` lines, which `remote-agent` now ignores (it says so): running `setup` once moves them into `settings.json`. Stopping it midway (Ctrl-C, end of input) writes nothing.

`check` proves the setup without spending tokens. It names each missing thing on its own line, then ends with a dry run, and exits 0 only when everything passes (it prints `ok` last):

- `remote.env` exists (without it, it says so and points to `setup`), sets the credential `remote.credential` names for `remote.harness` (`CLAUDE_CODE_OAUTH_TOKEN` by default) and no `REMOTE_*` lines left from before `settings.json`; the credential is checked as set, never printed, and not sent anywhere. A credential the harness does not take, a `remote.base_url` that is not an http or https URL, or a `remote.models` entry that is not `name=model` is named. A `remote.backend` is set.
- The backend's needs. `cluster`: `kubectl` on `PATH`, the kube context, and `kubectl auth can-i` to create SandboxClaims and `pods/exec` in the namespace. `docker`: the Docker daemon (`docker info`), the image present or pullable, and a note when the image's architecture differs from the machine's (it would run emulated). `ssh`: a login to the host with the configured key or password (a failure names which it tried), then the `docker` checks run on the host (container mode) or the tools bare mode needs (bare mode).
- The dry run, only when nothing is missing: acquire a sandbox, put a one-file snapshot in `~/work`, run a shell command that copies it to `~/out`, finds the harness's CLI (`claude` or `codex`) and runs `node --version` and `<cli> --version` (printed; a binary that is there but does not run, such as one missing a shared library, fails this step with its own error), get `~/out` back and compare, release. No model call. The sandbox is released even when a step fails, and the failing step is named.

By hand instead: put `CLAUDE_CODE_OAUTH_TOKEN=...` (from `claude setup-token`; or the credential `remote.credential` names) in `~/.config/dotagents/remote.env`, `chmod 600` it, and set the backend's Settings with `~/.agents/bin/settings set remote <key> <value> --machine` (see [Backends](#backends)). For `cluster`, that needs `remote.context`, a kube context that can create SandboxClaims and exec into pods in `remote.namespace` (`agents` by default), and `remote.pool`, the warm pool; neither has a default; for `docker`, Docker and the runner image; for `ssh`, a key or password login (see [Logging in](#logging-in); the password as `SSH_PASSWORD=...` in `remote.env`) to a host with Docker and the image (bare mode: the tools listed under [Bare mode](#bare-mode-trusted-hosts-only) instead).

Without a backend or a credential, skills run their subagents on this machine, as before.

No GitHub credentials are needed or sent: the PR, if any, is opened from the laptop.

## What the sandbox can reach

On the cluster: internet egress only: the model API (or your gateway) and package registries work, so agents can install dependencies and run tests. Cluster services and the LAN are blocked. It holds no GitHub credentials and no git remote, so it cannot read or push to any private repo. Anyone with admin rights on the cluster can still exec into a running pod and see the snapshot and the credential during a run.

## The runner image

[`runner/Dockerfile`](runner/Dockerfile) builds the image the `docker` and `ssh` backends run, and a cluster's SandboxTemplate can run too. It holds tools only, no credentials and no one's setup: a run sends its tokens through stdin and installs its own setup when it execs in. What a run can rely on:

- **User**: `node` (uid 1000), home `/home/node`, writable.
- **Tools**: Claude Code (pinned by `CLAUDE_CODE_VERSION`, auto-update off), node, git, `gh`, `jq`, `curl`, `python3` with `venv` and `pip` (Debian marks the system Python externally managed, so install packages into a venv).
- **GitHub auth**: git uses `gh auth git-credential` for `https://github.com`, so exporting `GH_TOKEN` is enough for clone, push and `gh`.
- **Idle**: the container runs `sleep infinity` under `tini` until a run execs in; removing it stops it at once.

`.github/workflows/runner-image.yml` builds it on every PR that changes it, runs a smoke test (each tool answers, as user `node`), and on `main` publishes `ghcr.io/rpvsilva/agent-runner:main` and a dated tag, for `linux/amd64` and `linux/arm64`. Every Monday it rebuilds without cache on the same pins, for Debian's security fixes. The package is public, so anyone can `docker pull` it without logging in. Renovate (`renovate.json`) opens one PR a week bumping the pins: the node base image's digest and Claude Code, each at least 3 days old.

To build your own: `docker build -t agent-runner:dev remote/runner`, then `~/.agents/bin/settings set remote image agent-runner:dev --machine`.

### One image per subagent

A subagent can run on its own image, e.g. `epic-implementer` on one with Python and `pr-reviewer` on a slimmer one. Build each image on this one (`FROM ghcr.io/rpvsilva/agent-runner:main`), so it keeps what a run relies on, then list them as `agent=image` entries in `remote.images`:

```sh
~/.agents/bin/settings set remote images "epic-implementer=ghcr.io/you/runner-py:1,pr-reviewer=ghcr.io/you/runner-slim:1" --machine
```

A run started with `--agent <agent>` (as every skill starts one) uses that agent's image; an agent not listed, or a run without `--agent`, uses `remote.image`. `REMOTE_IMAGE` set in the environment still wins, for that one run. This covers the `docker` backend and `ssh` in container mode. On `cluster` the image belongs to the warm pool's SandboxTemplate, so give each agent its own pool instead, as `agent=pool` entries in `remote.pools` (`REMOTE_POOL` wins the same way). Both are machine Settings only: a repo cannot pick the image your Claude token is sent into. `remote-agent check` checks every listed image as it checks `remote.image`, and a malformed entry (not `agent=value`, or an agent named twice) fails `check` and every run.
