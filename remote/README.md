# remote

Running subagents on a remote backend for compute only: a Kubernetes cluster, Docker on this machine, or a VM or PC over SSH. The laptop keeps the code, the git history and the orchestrating session; the backend gets what one subagent needs for one task and gives back a patch. It never touches a repo or GitHub, so it works for any project, including ones the machine's owners have no access to.

## Where the pieces live

- **The cluster side** lives in the cluster's GitOps repo: the agent-sandbox controller, the `agent-runner` image (`tools/agent-runner`, also used by the `docker` and `ssh` backends) and the `claude-runner` SandboxTemplate and warm pool (`ai-infrastructure/agents`).
  The image must ship shellcheck at the version in [`scripts/shellcheck-version`](../scripts/shellcheck-version): implementers run `tests/run.sh` there, and it fails on any other version. Bump the image there when the pin changes here.
- **This repo is the client**: [`scripts/remote-agent.sh`](../scripts/remote-agent.sh), driving one backend script from [`scripts/remote-backends/`](../scripts/remote-backends/).

## Use

```sh
~/.agents/bin/remote-agent [--attach PATH]... [--name TASK] [--] "<brief>" [worktree]   # or @brief.md, or - for stdin
~/.agents/bin/remote-agent --help   # the usage on stdout, exit 0; any other --option before the brief: the usage on stderr, exit 1
```

`install.sh` links the command there, so skills reach it from any project. Skills use it through [Remote subagents](../skills/_shared/conventions.md#remote-subagents): a subagent a skill marks remote-capable (today the implementer and test-tuner in `build-epic`, the test-tuner in `tune-tests` and the fix implementers in `security-audit`) runs here whenever `remote.env` exists. `--attach` copies a file or folder from outside the worktree (a task, a spec) to `~/attached/<name>` in the sandbox, read-only. `--name` names the task (e.g. a task's `TT-NN-<slug>`), made a valid label value (lowercase, `[a-z0-9-]`, at most 63 characters): every progress line on stderr starts with `[<task>]` (`[<run>]` without it), so several runs in parallel stay readable, and the backend labels the sandbox with it.

1. [`remote-agent-pack.sh`](../scripts/remote-agent-pack.sh) stages this machine's setup: `CLAUDE.md`, skills, agents, commands, rules, `~/.agents/{skills,hooks}`, and this repo's [`capped`](../scripts/capped) as `~/.agents/bin/capped`; `settings.json` cut down to permissions, model, plugins and the hooks that call `~/.agents/hooks`; MCP servers that need no env or headers. Credentials, history, transcripts, caches and settings `env` never leave the machine; what it leaves out is printed.
2. It copies the attachments (minus secret-looking files) and lists the worktree's tracked and unignored files, minus secret-looking ones (the `guard-secrets` rule), and checks the size (`REMOTE_MAX_MB`, 200 by default).
3. It prints the path of the run's live transcript, `<common git dir>/remote-agent/<run>/transcript.jsonl`, then acquires a sandbox from the backend (on the cluster: claims a warm one) and puts the setup and the snapshot in as tar streams, saying how long each took (`claimed in <N>s`, `sent setup and snapshot in <N>s`). The Claude token goes through stdin.
4. In the sandbox, [`remote-agent-sandbox.sh`](../scripts/remote-agent-sandbox.sh) reinstalls the plugins and MCP servers, commits the snapshot as a base, and runs Claude headless on the brief. Every shell command Claude runs (its Bash tool) goes through `capped` under the caps `remote.cap_mb` (`REMOTE_CAP_MB`, 2000 MB) and `remote.cap_secs` (`REMOTE_CAP_SECS`, 300 s), passed as arguments after the sandbox script since the backends pass argv, not the environment. The sandbox writes a small prefix script, `~/.agents/bin/capped-shell`, sets `CLAUDE_CODE_SHELL_PREFIX` to it after one probe through it, and says `== capped: shell prefix set (--mb N --secs N)`; Claude Code runs the prefix with the whole command line as one argument, and the prefix caps only Bash-tool command lines (they end with `pwd -P >| <file>`), running hooks and MCP servers as they are. A command over a cap is killed (`capped: killed: memory` or `capped: killed: timeout` in its output), and Claude carries on: the kill is no failed run. Each kill goes to `~/out/capped.log` as `capped: killed: <kind> <command>` and, within a second, to stderr, so it reaches `progress.log` even if the sandbox is lost after. When the probe fails (no `capped`, or no `python3` or `ps` to run it), the sandbox logs `== capped: unavailable` and the run goes on uncapped. Keep `cap_mb` under the sandbox's own memory limit, with room for Claude: the cap is per command, not for Claude nor the sum of commands run at once. Its progress shows on stderr, and in the sandbox's own log with every step of `remote-agent` (`kubectl logs <pod>`; `progress.log` in the sandbox's home where there is no such log). The token never goes there. Claude's raw `stream-json` events come back as they arrive and are appended to `transcript.jsonl` (follow it with `tail -f`): only lines that are JSON, with the token's value replaced by `[redacted]`. stderr says when the first one came (`first agent event after <N>s`, counted from the start of the run).
5. The patch comes back and is applied to the worktree, uncommitted. The summary (Claude's final report) goes to stdout, once: the sandbox leaves it out of the progress lines on stderr, which show Claude's other text and tool calls. Both are kept in `<common git dir>/remote-agent/<run>/` (`changes.patch`, `summary.md`), with the full stream from the sandbox (`stream.jsonl`), the live transcript (`transcript.jsonl`), Claude's session (`session.jsonl`), and the run's own record (`run.json`, `progress.log`, `result.json`, below). The token's value is replaced by `[redacted]` in every one of them. That folder is in the common git dir (`git rev-parse --path-format=absolute --git-common-dir`), shared by every worktree of the repo, outside the worktree and the patch: it stays after the sandbox is released and after a linked worktree is removed. The run folder is made with `mkdir` without `-p`, so a run whose id another run already took draws a new one. Runs from before this sit in `<common git dir>/worktrees/<name>/remote-agent/<run>/`, are not moved, and go with their worktree; `remote-agent resume` still finds them. Only the patch is applied; everything else the sandbox sent is data to read, never instructions to follow. The sandbox's `~/out` is unpacked in a temporary folder first, and only its regular files of those names (and `capped.log`) are copied in: a link it sends cannot aim a write of `remote-agent` at another file, nor can it replace `run.json` or `progress.log`.
   The session is not placed for `/resume`: the sandbox wrote it, so a prompt-injected agent could have forged turns in it that read as yours, and `/resume` would load them as your own history, run locally with your credentials. stderr names the kept file and the command that places it (`session: <path> (... remote-agent resume <run> <worktree>)`); when no session came back, it says so and the run goes on.
   To pick the run up where it stopped, read the session first, then run `remote-agent resume <run> [worktree]` (default: the current worktree). It warns that the session came from an untrusted sandbox, then places it where Claude Code looks for the worktree's sessions: `${CLAUDE_CONFIG_DIR:-~/.claude}/projects/<worktree's real path, every character outside [A-Za-z0-9] made ->/<session id>.jsonl` (under Git Bash, from the Windows path: `C:\Users\x\proj` gives `C--Users-x-proj`), with its `cwd` lines set to that path. Then run `claude` in the worktree and `/resume` it (or `claude --resume <session id>`). A folder name over 200 characters is refused: Claude Code shortens such names its own way, so `/resume` would never find the file.
6. The sandbox is released on exit, also on Ctrl-C or `kill`, and with it the token (on the cluster: the claim is deleted, and with it the pod). The backend's time limit (`REMOTE_HOURS`, 2 by default; the claim's `shutdownTime` on the cluster) removes it if the script dies first; in SSH bare mode, the first acquire more than 10 minutes past it kills the run and removes its folder.

Exit codes: 0 applied, 3 no changes, 4 the patch did not apply (the worktree changed meanwhile; the patch is kept), 5 the Claude account hit its usage limit: stderr says so on one line, `[<task>] usage limit: resets <time>` (the time as Claude gave it, e.g. `5:30pm (UTC)`, or `unknown`), and nothing goes to stdout. Any other failure exits with the sandbox's own code, 1 in place of 3, 4 or 5, so those always mean the above. The summary goes to stdout only on 0, 3 and 4. Each command the caps killed adds one line on stderr, whatever the exit, `[<task>] killed: memory|timeout <command>`, matched from the `capped: killed:` lines in `progress.log` (else from the `capped.log` that came back, kept beside it); a kill alone changes no exit code.

### What a run says about itself

From the moment its folder exists, every run keeps two files beside `transcript.jsonl`, and a third when it ends, so any reader (a Claude Code mod, `tail -f`, another tool) follows it from files instead of stderr:

- **`run.json`**: what the run is and where it stands. `run` (the folder's name), `name` (the `--name` as made a label value, else `null`), `worktree`, `started` and `ended` (epoch seconds), `pid` and `pid_start` (`remote-agent`'s process and its `ps -o lstart=` in the C locale, as a reader's `LC_ALL=C ps` prints it), `state`, `exit_code`, and `claim_s`, `send_s`, `first_event_s` (whole seconds; `null` until known). `state` is `starting` when the folder is made, `running` just before the sandbox run starts, then `done` on exit 0 or 3 and `failed` on any other (1, 4, 130 on Ctrl-C, 143 on `kill`), `exit_code` saying which. Each write goes to a temporary file then `mv`, so it is valid JSON at every read; it never holds the brief or the token, and a failed write never fails the run. A `kill -9` (or a reboot) runs no exit step: `starting` or `running` with `pid` not alive, or alive with another `pid_start`, means the run stopped without saying so.
- **`result.json`**: what the run came to, written by [`remote-agent-result.sh`](../scripts/remote-agent-result.sh) on every exit, also a failed or interrupted one (not after `kill -9`). `run`, `name`, `exit_code`; `status` (`done` on exit 0 or 3, else `failed`, as `run.json`'s `state`); `report_status` (the report's own `status:` line, e.g. build-epic's `done`, `blocked` or `plan-wrong`; `null` without one); `changed` (the files `changes.patch` touches, `[]` when it is empty, `null` when no patch came back); `follow_up` (the report's `follow-up:` lines, `[]` when none); `report_path` (`summary.md`, `null` when none came back); `duration_ms`, `num_turns`, `total_cost_usd` and `usage` (from the transcript's last `result` event; `duration_ms` from `run.json`'s times without one) and `model` (the transcript's `system`/`init` event). `complete` is `true` only on exit 0, 3 or 4 with a result event that is not an error. Anything unknown is `null`, never 0: a run that failed before Claude reported has `total_cost_usd: null`, while the usage-limit failure (exit 5) keeps the cost its error result shows. It is written through a temporary file then `mv`, with the token's value redacted, and a failed write never changes the exit code. A caller that lost stdout, stderr or `$?` reads the run's outcome here. `remote-agent result <name|run> [dir]` prints it without knowing the folder: for the run with that id, or the newest run (latest `run.json` `started`, then the `run.json` written last) whose `name` is `<name>` made a label value as `--name` makes it, among the repo's runs, old-location ones included, preferring runs whose `run.json` `worktree` is the caller's. One line on stderr and exit 1 when none matches, the argument is not a run or task name, or the newest match has no `result.json` yet (still running): never an older run's result in its place. Runs started at once, with stderr in a file or through `2>&1 | cat`, each keep their own folder, `progress.log` and `result.json`, so each is read right.
  It also holds `capped_kills` (each command the caps killed, `[{kind, cmd}]`: `kind` `memory` or `timeout`, `cmd` `null` when the line names none; `[]` when none), `killed` (the last kill's kind, else `null`) and `lost` (`true` when the run failed with an exit other than 3, 4 or 5 and no kill line, and a progress line says its container or pod was gone: `No such container`, `container not found`, `pod "..." not found`). So a cap kill reads apart from a lost sandbox.
- **`progress.log`**: every progress line stderr shows, as it comes, without the `[<task>]` tag, the token's value replaced by `[redacted]`. Its last line is the run's latest step.
- **Pruning**: `remote-agent prune --older-than <Nd|Nh> [--dry-run] [dir]` ([`remote-agent-prune.sh`](../scripts/remote-agent-prune.sh)) removes the run folders of the repo at `dir` (default the current one), in `<common git dir>/remote-agent/` and the old `<common git dir>/worktrees/<name>/remote-agent/`, older than N days (`d`) or hours (`h`), N at most 999999: by `run.json`'s `ended`, else `started`, else the folder's mtime. It never removes a live run: `starting` or `running` with `pid` alive and the same `pid_start` (where `ps` prints no start times, as in Git Bash, a `pid` alive is enough); one whose `pid` is gone or reused stopped, and goes. A folder whose name is no run name (`^[A-Za-z0-9][A-Za-z0-9._-]*$`) is left, with one line on stderr, and a link is neither followed nor removed. It prints `removed <path>` per folder, then `removed N runs`; `--dry-run` prints `would remove ...` and removes nothing. Any other age, or an unknown argument, is refused with the usage, exit 1. It does not touch copies a skill made elsewhere (build-epic's `<run>/remote/<task>.json`).

## Backends

The `remote.backend` Setting names the backend; unset, remote runs are off and skills run subagents on this machine. Every remote Setting is declared, with its default and meaning, in [settings.json](settings.json), and lives at the machine Level (`~/.config/dotagents/settings.json`, through `~/.agents/bin/settings` or the `configure` skill); a repo can only set `remote.allowed` to `false`, which keeps its worktree snapshots on this machine, and `remote.open_pane` (true), whether Claude Code's `remote-runs` mod opens its pane when a run starts. `remote.max_sandboxes` (4) is how many remote subagents skills run at once, whatever the skill: set it to what the backend holds (the warm pool's size, the SSH host's cores; a claim on a full pool waits `REMOTE_CLAIM_TIMEOUT`, then fails). It is counted apart from a skill's `max_parallel`, which caps subagents on this machine; skills keep to it, `remote-agent` itself does not count runs. Each Setting's `REMOTE_*` variable, when set in the environment, overrides it for one run; the names below are those variables. Each backend is a script, `scripts/remote-backends/<name>.sh`. `remote-agent` exports every `REMOTE_*` setting to it (never the Claude token) and drives it with these operations only, so packing, secret filtering, the in-sandbox run, keeping results and exit codes stay the same on every backend:

| Operation | Does |
|---|---|
| `acquire <run>` | Gets a sandbox that removes itself after `REMOTE_HOURS`; prints its handle. |
| `put <run> <handle> <dir>` | Extracts the tar stream on stdin under the sandbox's `$HOME/<dir>`. |
| `run <run> <handle> <argv>...` | Runs the command in the sandbox with stdin, stdout and stderr streamed; returns its exit code. |
| `get <run> <handle> <dir>` | Writes a tar of the sandbox's `$HOME/<dir>` on stdout. |
| `release <run>` | Removes the sandbox, even after a half-done `acquire`; with `REMOTE_KEEP=1` keeps it and says what it kept. |
| `check` | Names, one line each, what this backend needs and is missing; fails when anything is. Used by `remote-agent check`. |
| `ping` | Probes the backend in a few seconds (cluster: `kubectl version --request-timeout=5s`; docker: `docker info`; SSH: a login with `ConnectTimeout=5`, then `docker info` on the host in container mode); on failure prints the error on one line and fails. Used by `remote-agent ready`. |

Shared helpers for backends live in `scripts/remote-backends/lib.sh`, which is not a backend.

### `cluster` (default)

An agent-sandbox SandboxClaim on a warm pool, driven with `kubectl exec`; the handle is the pod. Settings: `REMOTE_CONTEXT` (kube context, `maxibombo`), `REMOTE_NAMESPACE` (`agents`), `REMOTE_POOL` (warm pool, `claude-runner`), `REMOTE_HOURS` (the claim's `shutdownTime`, 2), `REMOTE_KEEP=1` (keep the claim: `kept sandboxclaim/<run>`), `REMOTE_CLAIM_TIMEOUT` (seconds to wait for the claim to be Ready, 180; on a timeout the claim's conditions are printed, and a claim the controller fails stops the run at once with its reason). The claim and its pod carry the labels `sandbox.users.io/remote-agent-run=<run>` and, with `--name`, `sandbox.users.io/remote-agent-task=<task>`: `kubectl get pods -L sandbox.users.io/remote-agent-task` tells the runs apart, and `kubectl logs -f <pod>` follows one. The labels sit under `sandbox.users.io` because agent-sandbox rejects pod labels outside its allowed domains (`AllowedLabelDomains`, default `sandbox.users.io`). Needs a kube context that can create SandboxClaims and exec into pods in the namespace.

### `docker`

A fresh container of the runner image on this machine for each run, driven with `docker exec`; the handle is the container, named after the run. It runs `sleep <REMOTE_HOURS*3600>` under `--rm`, so it removes itself after `REMOTE_HOURS` if `remote-agent` dies; otherwise `docker rm -f` removes it at the end, also on failure, Ctrl-C or `kill`. Like the cluster's pods, it carries the labels `sandbox.users.io/remote-agent-run=<run>` and, with `--name`, `sandbox.users.io/remote-agent-task=<task>`: `docker ps --filter label=sandbox.users.io/remote-agent-task` lists the named runs, and `docker logs -f <run>` follows one. Needs only Docker and the image. Settings, in `remote.env`:

- `REMOTE_BACKEND=docker`.
- `REMOTE_IMAGE`: the runner image, `ghcr.io/xgeekshq/agent-runner:main` by default. It is private: log in once with `docker login ghcr.io` (your GitHub user and a token with `read:packages`), or build it from `tools/agent-runner` in the cluster's GitOps repo (`docker build -t agent-runner:local tools/agent-runner`) and set `REMOTE_IMAGE=agent-runner:local`.
- `REMOTE_PLATFORM`: passed to `docker run --platform` when set (e.g. `linux/amd64`); unset, Docker picks this machine's architecture.
- `REMOTE_HOURS` (2) and `REMOTE_KEEP=1` (keep the container: `kept container <run>`; it still removes itself after `REMOTE_HOURS`).

**Apple Silicon** needs the image published for `linux/arm64` as well as `linux/amd64`, or built locally as above. An amd64-only image runs under emulation with `REMOTE_PLATFORM=linux/amd64`, but slowly.

The container gets Docker's default network: internet egress, and whatever this machine's network reaches. Anyone who can run `docker` here can see the snapshot and the token during a run.

### `ssh`

A VM or PC reached with `ssh`. In container mode (the default) it is the `docker` backend run on that host: a fresh container of the runner image per run, each `docker` command sent as one `ssh -T <login options> <host> '<command>'` call (see [Logging in](#logging-in)) with every word single-quoted, so any login shell (bash, zsh, dash) runs it as written. Files travel as tar streams through the connection, and the token through stdin: no `scp`, no temp files on either side, and the token never in `ssh` arguments. Containers are named after the run and labelled as for `docker`, so several runs can share the host; each is removed at the end, and `--rm` with its `sleep` removes it after `REMOTE_HOURS` if `remote-agent` dies. Settings, in `remote.env`:

- `REMOTE_BACKEND=ssh`.
- `REMOTE_SSH_HOST`: the ssh destination, `user@host` or an alias from `~/.ssh/config` (where a port, key or jump host go).
- `REMOTE_SSH_KEY`: a private key file to log in with, alone (`-i <file> -o IdentitiesOnly=yes`; a leading `~/` is this machine's home). Unset: the ssh agent's keys or `~/.ssh/config`'s.
- `REMOTE_SSH_MODE`: `container` (the default) or `bare` (see [Bare mode](#bare-mode-trusted-hosts-only)). Any other value stops the run, naming both.
- `REMOTE_SSH_SUDO` (`remote.ssh_sudo`, false): run every `docker` command on the host as `sudo -n docker`, for an SSH user outside the `docker` group who has passwordless sudo. Container mode only.
- `REMOTE_IMAGE`, `REMOTE_PLATFORM`, `REMOTE_HOURS` and `REMOTE_KEEP=1` as for [`docker`](#docker), applied on the host.

In container mode the host needs:

- **An SSH login** with a key or a password (see [Logging in](#logging-in)). `remote-agent check` tries it.
- **Docker** the SSH user may use: in the `docker` group (`sudo usermod -aG docker <user>`, then log in again), or through passwordless sudo with `remote.ssh_sudo` set to `true`. Either way the user can act as root on the host. When plain `docker` is refused but `sudo -n docker` works, `remote-agent check` says so and gives both fixes; sudo that asks for a password does not work, since nothing may wait on a prompt.
- **The image**: log in once on the host (`ssh -t <host> docker login ghcr.io`; with `remote.ssh_sudo`, `sudo docker login ghcr.io`, as root pulls) or build it there, and set `REMOTE_IMAGE` to its tag. Pick a `REMOTE_PLATFORM` or image that matches the host's architecture.

#### Logging in

Every call logs in on its own, in the background, so nothing may wait on a terminal. Two ways, both set by `remote-agent setup`:

- **A key**: from the ssh agent or `~/.ssh/config` (nothing to set), or a key file in `REMOTE_SSH_KEY`. An encrypted key file needs its passphrase in the agent (`ssh-add <file>`) or as the `SSH_KEY_PASSPHRASE` Secret.
- **A password**: the `SSH_PASSWORD` Secret.

The password and the passphrase are Secrets, in `~/.config/dotagents/remote.env` beside the Claude token (mode 600), never Settings, never in `ssh` arguments, never sent to the host's commands. With neither set, every call runs with `-o BatchMode=yes`: no prompt at all. With either set, keys are still tried first, then one password try (`-o BatchMode=no -o NumberOfPasswordPrompts=1`), and ssh asks `scripts/remote-ssh-askpass.sh` (`SSH_ASKPASS` with `SSH_ASKPASS_REQUIRE=force`, OpenSSH 8.4 or later on this machine) instead of the terminal. It answers a password prompt with `SSH_PASSWORD` and a passphrase prompt with `SSH_KEY_PASSPHRASE`, and nothing else: an unknown host key's question gets no answer, so the login fails as with `BatchMode`. Add the host key first with one interactive `ssh <host> true`.

**Who can see the code and the token during a run** in container mode: the host's root and every member of its `docker` group, since they can `docker exec` into the container or inspect it. Use a host only you (and people you trust with the token) administer. The container gets Docker's default network on the host: internet egress, and whatever the host's network reaches.

#### Bare mode (trusted hosts only)

With `REMOTE_SSH_MODE=bare` the run happens directly on the host, as the SSH user, with no container. **This is weaker isolation**: the run shares the OS user with that user's own setup and with other runs, has no network limits beyond the host's own, and the SSH user (and the host's root) can read the code and the Claude token while a run lives. Prefer container mode whenever the host has Docker or is shared with anyone else.

- Each run gets its own folder, `$REMOTE_SSH_DIR/<run>` (mode 700), used as its `HOME`, with `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME` and Claude Code's config (`CLAUDE_CONFIG_DIR`) inside it: the setup, plugins, MCP servers, token and files stay apart from the host user's `~/.claude` and from other runs. At the end, whatever still runs for the run is killed (by the pid and process group recorded in the folder's `.pid`; its own group via `setsid` where the host has it, else the process and its children via `pkill -P`), even a process that ignores `TERM`, then the folder is removed; `REMOTE_KEEP=1` still kills the run but keeps the folder (`kept run folder ...`) until an acquire removes it under the rule below. Only the run's own processes are signalled: a recorded pid counts as the run's only while its working folder is inside the run folder (read from `/proc`, else `lsof`), so a pid since reused by another process is left alone.
- The host needs the same SSH login as container mode, and no Docker.
- Before anything is sent, the host is checked for `bash`, `tar`, `git`, `jq`, `node` and `claude` on the SSH user's `PATH` (non-interactive login: set it in the shell's non-interactive startup file); each missing one is named and the run stops. Installers often put them where only an interactive shell looks (nvm's `~/.nvm`, Claude's `~/.local/bin`), which a command run over ssh does not see: link them into `/usr/local/bin` (`sudo ln -sf "$(command -v node)" /usr/local/bin/node`, the same for `claude`, from an interactive shell; redo the node link after switching versions with nvm). `remote-agent check` runs both with `--version`, so one that is found but does not start (Node from nvm on Ubuntu 24.04 needs `sudo apt-get install libatomic1`) is named with its error.
- A client that dies leaves its folder behind; the next run's acquire removes it, but never a live run. Each run records its own expiry in its folder's `.expires` (the host's clock plus that run's `REMOTE_HOURS`, set at acquire), and while it runs a host loop touches `.heartbeat` every 60 seconds. Acquire removes a folder when the host's clock is past its `.expires` and its `.heartbeat` is missing or older than 3 minutes, so another client's smaller `REMOTE_HOURS` cannot cut a run short. `REMOTE_HOURS` is still a hard limit: once the clock is more than 10 minutes past a folder's `.expires`, acquire removes it whatever its heartbeat, first killing what still runs there as release does, so a run whose client died and whose command never ends goes with the next acquire after that. A folder with no `.expires` (left by an older client) is removed when its mtime is older than the acquiring client's `REMOTE_HOURS`.
- The sandbox log is `progress.log` in the run folder (there is no container log), never the host's `/proc/1/fd/1`, even as root.
- Settings: `REMOTE_SSH_DIR`, the run folders' root on the host, absolute or relative to the SSH user's home (`.remote-agent/runs` by default); `REMOTE_HOURS` and `REMOTE_KEEP=1` as above. `REMOTE_IMAGE` and `REMOTE_PLATFORM` do not apply.

## Setup, once

```sh
~/.agents/bin/remote-agent setup   # asks for the backend, its Settings and a Claude token
~/.agents/bin/remote-agent check   # checks the backend's needs, then a dry run
~/.agents/bin/remote-agent ready   # whether skills send this repo's subagents to the backend, and if not, why
```

`ready` checks the Settings and the token, then probes the backend (its `ping`, a few seconds at most). It prints the backend's name and exits 0, or prints one line saying why not and exits 1: a missing Setting or token, `remote.allowed` false, or `<backend> backend not reachable: <the error>` (e.g. `cluster backend not reachable: context maxibombo: Unable to connect to the server: dial tcp ...: connect: no route to host`).

`setup` asks for the backend and its details (cluster: kube context, by default the saved one or else the current one, namespace and pool; SSH: host, login (a key, from the agent or a key file with an optional passphrase, or a password) and mode; Docker: nothing more; the runner image for Docker and SSH container mode), and writes them as Settings to `~/.config/dotagents/settings.json`, keeping those it does not ask about (`hours`, `keep`, ...). It then asks you to run `claude setup-token` in another terminal and paste the token, which it reads without echo and never prints; enter keeps the token already there. The token, the SSH password and the key passphrase are Secrets, read the same way, so they go alone to `~/.config/dotagents/remote.env`, readable only by you (mode 600); choosing one SSH login drops the other's Secret. A `remote.env` from before `settings.json` still holds `REMOTE_*` lines, which `remote-agent` now ignores (it says so): running `setup` once moves them into `settings.json`. Stopping it midway (Ctrl-C, end of input) writes nothing.

`check` proves the setup without spending tokens. It names each missing thing on its own line, then ends with a dry run, and exits 0 only when everything passes (it prints `ok` last):

- `remote.env` exists (without it, it says so and points to `setup`), sets `CLAUDE_CODE_OAUTH_TOKEN` and no `REMOTE_*` lines left from before `settings.json`; the token is checked as set, never printed, and not sent anywhere. A `remote.backend` is set.
- The backend's needs. `cluster`: `kubectl` on `PATH`, the kube context, and `kubectl auth can-i` to create SandboxClaims and `pods/exec` in the namespace. `docker`: the Docker daemon (`docker info`), the image present or pullable, and a note when the image's architecture differs from the machine's (it would run emulated). `ssh`: a login to the host with the configured key or password (a failure names which it tried), then the `docker` checks run on the host (container mode) or the tools bare mode needs (bare mode).
- The dry run, only when nothing is missing: acquire a sandbox, put a one-file snapshot in `~/work`, run a shell command that copies it to `~/out`, finds `claude` and runs `node --version` and `claude --version` (printed; a binary that is there but does not run, such as one missing a shared library, fails this step with its own error), get `~/out` back and compare, release. No Claude API call. The sandbox is released even when a step fails, and the failing step is named.

By hand instead: put `CLAUDE_CODE_OAUTH_TOKEN=...` (from `claude setup-token`) in `~/.config/dotagents/remote.env`, `chmod 600` it, and set the backend's Settings with `~/.agents/bin/settings set remote <key> <value> --machine` (see [Backends](#backends)). For `cluster`, that needs a kube context (`maxibombo` by default, `remote.context` to change) that can create SandboxClaims and exec into pods in `agents`; for `docker`, Docker and the runner image; for `ssh`, a key or password login (see [Logging in](#logging-in); the password as `SSH_PASSWORD=...` in `remote.env`) to a host with Docker and the image (bare mode: the tools listed under [Bare mode](#bare-mode-trusted-hosts-only) instead).

Without a backend or a token, skills run their subagents on this machine, as before.

No GitHub credentials are needed or sent: the PR, if any, is opened from the laptop.

## What the sandbox can reach

On the cluster: internet egress only: Anthropic and package registries work, so agents can install dependencies and run tests. Cluster services and the LAN are blocked. It holds no GitHub credentials and no git remote, so it cannot read or push to any private repo. Anyone with admin rights on the cluster can still exec into a running pod and see the snapshot and the token during a run.
