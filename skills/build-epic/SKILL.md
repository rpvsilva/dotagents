disable-model-invocation: true

Build an epic as **tickets** made of **tasks**. A ticket is one tracker issue: its own branch `feat/<ticket-slug>` and one PR into the run's **base** (the default branch, or the integration branch `--into` names), so several developers can split an epic by ticket. A task is one implementer's slice of a ticket: its own branch, merged into the ticket branch as one merge commit once the Checks pass, with no PR of its own. The ticket branch stays on this machine until the ticket ships; its PR then lists every task with that commit, and its one deep review covers them all.

Work runs in **lanes** ([planner-brief.md](planner-brief.md) pass B): tickets that share files run one after another, and only lanes with disjoint write sets run in parallel. A run that fills fewer slots and merges cleanly beats one that fills them all and spends its runs on conflicts.

You are the **orchestrator**: you start subagents, run the [step scripts](#step-scripts) that track statuses and open and merge PRs, and talk to the human. Keep your context **thin**: you read the run folder's short files (ticket and task headers, the `Checks` section of `map.md`, reports), not the code or the tracker; the one exception is verifying review findings in steps 6 and 7. Every heavy read happens in a subagent that writes its result to a file and returns a 4-line block ([Subagents](#subagents)).

Input: an epic or issue (link or ID, on any tracker), or plain text. Optional: `--parallel N`; `--explore` to always run the explorers; `--into <branch>` to build into an integration branch: every ticket branch is cut from it and every ticket PR opens against it (it beats the `base` Setting).

## Run folder

`~/.agents/runs/<repo>/<epic-slug>/`: `<repo>` is the repo folder's name, `<epic-slug>` the tracker ID plus a few words (`gh-12-due-dates`). It holds:

- `run.md`: the repo's path, its default branch, its remote and the run's identity (`Repo:`, `Default:`, `Remote:`, `Identity:`), and the epic's issue when it has one (`Epic:`), written by `init_run.py` in step 1. Every step script reads it, never the current folder.
- `spec.md`, `areas.md`, `notes/<area>.md`, `map.md`: written by the planner and explorers.
- `tickets/TT-<slug>.md`: one per ticket. Its `Status:` line is `ready`, `claimed` (another developer builds it), `building`, `in-review` (its PR waits on a human), `merged` or `blocked`. The step scripts add its `PR:` line (the one `ship_ticket.py open` opens) and its `Claimed by:` line (`tracker_cmd.py claims`).
- `tasks/TT-NN-<slug>.md`: one per task, `TT` its ticket. Its `Status:` line is `ready`, `in-progress`, `done` (merged into the ticket branch) or `blocked`. Its optional `Tier:` line is the planner's: `high` gets the task its own review before it merges (step 6). `finish_task.py` appends to its `Writes` line every path it changed outside it and adds its `Finished: <UTC>` line the first time it commits; `merge_task.py` adds its `Done: <UTC>` and `Commit: <merge commit>` lines when it sets it `done`.
- `plan/TT.md`: what you decided for a ticket at approval (the answers to `spec.md`'s open questions that bear on it, any change to its scope), put on its issue by `tracker_cmd.py planned`.
- `logs/<id>-<step>.log`: every git, gh and test output of a step script, named on its `FAIL` line; beside them, the PR bodies (`<id>-pr-body.md`) and review payloads (`PR<n>-review.json`) the scripts sent.
- `reports/<id>.md`: each subagent's full report, written by the subagent (a remote one's by you, from its stdout): `<id>` is `plan-A`, `plan-B` or `plan-revise-<n>` for the planner, `explore-<area>` for an explorer and `TT-NN` for an implementer. Beside them, `reports/<id>.checks.json`: each suite `merge_task.py` ran, with its time and result.
- `remote/<TT-NN>-<remote run>.json`: the `result.json` of each remote run of a task (a retried task has several), copied by `finish_task.py`; [telemetry](../telemetry/SKILL.md)'s `--by-role --run-folder` and `run_metrics.py` add their cost to the run's.
- `state.md`: the one-screen state the run continues from (every ticket's line, the tasks in flight, what needs the human, its first 9 items then `+N more`, the next actions; at most 40 lines for 10 tickets), written by `status.py <run> --write` after each shipped ticket.
- `tracker.json`: the run's identity, the human's login, the labels created and the tracker updates held while the identity was away (`steplib/tracker.py`).
- `decisions.md`: the run's rules, decided once ([decide.py](scripts/decide.py) and [setup.py](scripts/setup.py) are its only writers; never edit it by hand). Header lines `base:` (the run's base, when it is not the default branch; every step script reads it, and an unset one means the default branch), `ci:` (on|off, from `setup.py`; with `off`, the ticket PR's body says the local `Checks` runs are the proof), `merge_identity:` (app|human, recording the `merge_identity` Setting), `human:` (the human's login, as recorded), `review_before_agent_merge:` (yes|no) `test_command:` (the one line every agent runs the tests with, from `setup.py`) and `caps:` (`<mb> <secs>`: each test command's memory and time caps on this machine, from `setup.py`: the `cap_mb` Setting, else the machine's memory share per slot, and `cap_secs`; exported ahead of every suite as `CAPPED_MB` and `CAPPED_SECS` defaults, so a remote run keeps its sandbox's own); then the **Authorizations** table, one row per leave-for-human clause of the repo's rules (`clause | waived | quote`, waived yes|no|ask, with `\` and `|` escaped by a backslash); then the **Decisions**, the human's words verbatim, one dated line each, a multi-line one continuing on lines indented two spaces. Every reviewer gets its path.
- `env/`: the run's one test environment, made by `map.md`'s `Setup` (`setup.py`, step 1); `env/.setup-done` marks it made.
- `skips.md`: the tools the suite skips without, one row each with its skip reasons, from one run of every Checks command (its `--all` form when `map.md` names one) in a throwaway worktree of the base (`setup.py`).
- `worktrees/TT-NN/` (one per task being built, from `start_task.py`) and `worktrees/TT/` (one per ticket being shipped, from `ship_ticket.py open`).

Only the step scripts and you change `Status:` and `PR:` lines; subagents leave them alone.

When the folder already exists, **resume**: run `resume.py <run>`. It sets each `in-review` ticket whose PR merged to `merged`, sets `done` every `in-progress` task already merged into its ticket branch, leaves every other `in-progress` task with a `Finished:` line for **Merge** in step 6, and sends the rest back to `ready` (worktree and branch removed). Then run `status.py <run> --write`, read `state.md`, and continue at the first step whose done-condition is not met.

### Step scripts

Every routine git and gh step is one command: `python3 -I ~/.agents/skills/build-epic/scripts/<step>.py <run> <id> [...]`, written below as `<step>.py <run> ...`. Each works from any folder, prints one line, `OK <id> <state> [details]` or `FAIL <id> <reason> (log: <path>)`, and exits non-zero on `FAIL`. Act on that line; open the log only to understand a `FAIL` or to hand it to a subagent. Never compose the git or gh commands a script runs yourself: when a step fails in a way this file does not cover, tell the human with the log path. Transient GitHub failures are retried by the scripts (waits of 2, 4, 8 and 16 s, scaled by `BUILD_EPIC_RETRY_SLEEP`, which tests set to 0). Every `gh` call a script makes, for PRs and the tracker alike, and the merge rule it runs, act as the run's **identity**: `run.md`'s `Identity:` line. When it names a command (the `identity_command` Setting, e.g. this repo's `scripts/gh-app-token.sh`), each call gets a fresh token from it, so no wait outlives the token, and `FAIL <id> identity-token` means the command failed. `Identity: login` acts as the current `gh` login. `status.py <run>` is the one that prints a table: one line per ticket, its tasks under it, with status, PR, blockers and title. `status.py <run> --line <TT>` prints the ticket's one line for the human (status, PR, title and what it waits on), `status.py <run> --report` adds, below the table, a `## Not exercised here` section listing each ticket's saved skip reasons (none saved, no section), and `status.py <run> --write` writes `state.md` (`OK run state <path>`).

## Subagents

| Agent | Brief | Writes |
|---|---|---|
| `epic-planner` | [planner-brief.md](planner-brief.md) | `spec.md`, `areas.md`, `map.md`, `tickets/`, `tasks/` |
| `epic-explorer` | [explorer-brief.md](explorer-brief.md) | `notes/<area>.md` |
| `epic-implementer` | [implementer-brief.md](implementer-brief.md) | commits on its task branch |
| `pr-reviewer`, `security-reviewer` | started by [review-pr](../review-pr/SKILL.md) (steps 6 and 7) | nothing: they return findings |

Start and limit them as in [Subagents](../_shared/conventions.md#subagents): at most **N** at once (the **slots**).

Each subagent's **description** (the short label your harness shows and saves with it, where it has one) starts with its role and a colon, so a saved run files its cost under that role ([telemetry](../telemetry/SKILL.md) `--by-role`): `plan: A`, `plan: B` or `plan: revise-<n>` for the planner, `explore: <area>` for an explorer, `implement: TT-NN <title>` for an implementer, `fix: TT-NN` for a fix-round task's implementer, `resolve: TT-NN` for one sent back to resolve conflict markers, and for reviewers, by review-pr mode, `review: TT-NN` (a high-tier task's review before it merges), `ticket-review: PR <n>`, `re-review: PR <n>` and `security: PR <n>` for the security reviewer. These are the roles the extractor saves (`ROLES` in `adapters/claude/telemetry/extract.py`); a description with no listed prefix is saved as `other`. Each subagent in a saved run also holds its `cost` at the prices of the save (`null` when a model has no price), and the run its `pricingAsOf`.

An implementer or a reviewer runs remotely when [Remote subagents](../remote-subagents/SKILL.md) lets its agent run there (the `needs.json` holding its brief declares it, `remote-agent ready` exits 0 and the human did not ask for `--local`); otherwise it runs here as below. For an implementer, `task_prompt.py <run> <id> --remote` writes its prompt (below) and prints `OK <id> remote prompt=<file> args=<arguments>`: run `~/.agents/bin/remote-agent` with those arguments, as printed. They name it after its task's file (`--name TT-NN-<slug>`), attach what its prompt names as `~/attached/<name>` (its task, `spec.md`, `map.md` and `notes/`) and dispatch into `<run>/worktrees/TT-NN`. Send `remote-agent`'s stdout (only) to `<run>/reports/<id>.md`; on exit 0 or 3, run `report_check.py <run> <id> --from-report`: it checks the block ending that file. Act on its exit code as that skill's step 4 says, except the commit: a remote run leaves its changes uncommitted, and `finish_task.py` (step 6, **On a report**) commits them and catches the task up with the ticket branch. It also copies each of the task's runs' `result.json` (its cost, turns and outcome) to `<run>/remote/<TT-NN>-<remote run>.json`, finding the runs by their `--name` and the task's worktree, so keep that name `TT-NN-<slug>` and dispatch into `<run>/worktrees/TT-NN`: another name or folder loses the remote run's cost. A high-tier task's review (step 6) always runs here: it has no PR to give a remote reviewer. Any other reviewer runs remotely through [review-pr](../review-pr/SKILL.md)'s **Remotely** branch (its step 3), named `review-<PR>-<sha7>` (`security-<PR>-<sha7>` for the security reviewer). Once it ends, write what `remote-agent result <name>` prints to `<run>/remote/<name>.json`, so telemetry adds its cost to the run's. Its report, copied to `<run>/reviews/<PR>-<sha7>.md` as that branch says, is verified and posted here with `post_review.py`, byte for byte, as a local reviewer's is. The planner and explorers write into the run folder, so they always run here.

Every **prompt** lists paths, never what the files hold: the brief's path, then one `<input>: <value>` line per input the step names, the report file last ([Subagents](../_shared/conventions.md#subagents)). An implementer's prompt is never written by hand: `task_prompt.py <run> <id>` writes it to `<run>/prompts/<id>-<n>.md` from one template, here and remote alike (`--remote`: the same lines, with `~/work`, `~/attached/<name>` and `~/out/report.md` for the paths), and prints `OK <id> local prompt=<file> agent=<agent>`: start that agent with that file's text. Its options add the lines a step below asks for: `--resolve <files>` (a resolver), `--cap <note>` (a cap note), `--failure <file>` (a red suite's log) and `--reissue` (a report that broke the brief). For an implementer here, it writes:

```
You are an epic-implementer. Follow ~/.agents/skills/build-epic/implementer-brief.md.
task: <run>/tasks/TT-NN-<slug>.md
run: <run>
worktree: <run>/worktrees/TT-NN
ticket branch: origin/<ticket-branch>
test_command: <decisions.md's test_command:, as written>
report: <run>/reports/TT-NN.md
```

Once `setup.py` has run, every prompt carries that `test_command:` line, copied from `decisions.md` as written (reviewers too; the reviewers get it through review-pr's `--run`): agents run the tests with it, and never build an environment of their own. A remote one gets it too; it runs `map.md`'s `Setup` itself only when the command names `<run>/env/`, a folder only this machine has.

Every subagent **reports** as [Reports](../_shared/conventions.md#reports) says: its full report to `<run>/reports/<id>.md` ([Run folder](#run-folder)), then a final message that is only this block, at most 400 characters:

```
status: done | blocked | plan-wrong
changed: <paths, or the last commit SHA>
why: <one line, when status is not done>
follow-up: <implementers: work a later task must pick up; may be empty>
```

Pipe that message to `report_check.py <run> <id>` (a code fence wrapping it is allowed). `OK <id> <status>`: act on the block alone, and open the report file only on `blocked` or `plan-wrong`, or where a step below reads it. `FAIL <id> brief-violation <details>`: do not read the message further; handle it as [Reports](../_shared/conventions.md#reports) says. For an implementer, a new agent's prompt is the one `task_prompt.py <run> <id> --reissue` writes (`--remote` when it ran remotely): it keeps the report that broke the brief in `<run>/prompts/`, where the next run's report cannot overwrite it, and names it on a `reissue:` line.

## Tracker

Keep the tracker in step with the build. Each ticket's `Issue` line names its issues, and every update below applies to each of them; with plain-text input there is none, and you skip this. The scripts make every GitHub update as the run's identity ([Step scripts](#step-scripts)), each only while the active login is still the one (the login of its first update, kept in `tracker.json`). When another session switched accounts, the update is held and the script fails `identity-changed`: keep building, and ask the human to switch back. Once they have, `tracker_cmd.py <run> flush` applies the held updates in order (every later tracker update applies them first too).

When the `tracker` Setting names another tracker, `tracker_cmd.py` touches nothing and its line ends `manual tracker=<name>`, and `start_ticket.py` adds `started=manual`: make that update yourself through the tracker's connector, as the bullet says.

- **Claimed**: an issue assigned to anyone but the human you work for belongs to another developer. `tracker_cmd.py <run> claims` (step 5) sets each `ready` ticket with such an issue to `claimed` and writes who on its `Claimed by:` line. `start_ticket.py` claims each ticket you start by assigning its issues to the human.
- **Planned**, once the human approves the plan (step 5) and again after each approved re-plan: first write `<run>/plan/TT.md` for each ticket the approval decided something about (the answers decided for `spec.md`'s open questions that bear on it, any change to its scope or acceptance criteria), then run `tracker_cmd.py <run> planned`. It puts one comment on every ticket's issue, claimed ones included, starting with the marker `<!-- build-epic-plan -->`: `plan/TT.md`, then the ticket's tasks (number, title, blocked by). An issue that already holds a marked comment has it edited, so each issue carries one current plan. `map.md` stays out: it is for implementers.
- **Started**, when a ticket starts: `start_ticket.py` adds the `in progress` label (created once per run) and assigns each issue to the human. With `started=manual` on its line (the `in_progress` Setting is set, e.g. a GitHub Projects status field, or the `tracker` Setting names another tracker), mark the issues started yourself as that Setting says.
- **Blocked**, when a task ends `blocked` or `plan-wrong`: `tracker_cmd.py <run> blocked <TT-NN> "<why>"` adds the `blocked` label to its ticket's issues and one comment, `Blocked: task TT-NN (<title>): <why>`. Once a re-plan or fix lets the task run again, `tracker_cmd.py <run> unblocked <TT>` removes the label.
- **Done** belongs to the ticket PR's merge: `ship_ticket.py <run> <TT> merge` closes the ticket's issues when the PR's own base (its `baseRefName` on GitHub) is the default branch. Into an integration branch it closes none: it labels each issue `merged-to-<base>` (landed on that branch) and leaves it open, to close once the base reaches the default branch; the [Report](#report) says so.
- **Epic done**: after each ticket ships, run `tracker_cmd.py <run> close-epic`. It closes the epic's issue (`run.md`'s `Epic:` line, or give its number) once every ticket's issue is closed (`OK epic closed #<n>`); until then it names the ones still open (`OK epic open #<a> ...`) and changes nothing.

## Steps

1. **Set up.** [Learn the rules](../_shared/conventions.md#learn-the-rules) with notes file `.agents/build-epic-notes.md` (test commands, areas to avoid) and the `tracker`, `max_parallel`, `in_progress`, `cap_mb`, `cap_secs`, `merge_command`, `identity_command` and `base` Settings, and the [ship-pr](../ship-pr/SKILL.md) rules from its step 1: commit convention, merge rule and the identity PRs are opened and merged as. When the merge rule is a command (this repo's `scripts/merge-pr.sh`), it belongs in the `merge_command` Setting, so the scripts merge ticket PRs by it: when that Setting is unset, ask the human to set it ([configure](../configure/SKILL.md)); a repo with a `.review-gate.yml` refuses ticket merges into the default branch without it. Likewise, when the rules name an identity (this repo's `GH_TOKEN="$(scripts/gh-app-token.sh)"`), its token command belongs in the `identity_command` Setting; unset, the scripts act as the current `gh` login. When the run folder exists, resume it (see [Run folder](#run-folder)); otherwise create it and run `init_run.py <run> <repo> [--epic <n>]`, `--epic` naming the epic's issue when the input is one (`OK run initialised repo=<path> default=<branch> remote=<url> identity=<command|login>`): the identity is decided here, once per run. On a new run, decide the **base**: `--into <branch>`, else the `base` Setting, else the default branch; when it is a branch other than the default, record it with `decide.py <run> set base <branch>` before anything else runs, since every step script reads it from `decisions.md`. Never change it by hand later; a new base mid-run goes through `catch_up.py` (step 6). The `merge_identity` Setting (app|human, default `app`) decides who merges: `app` when the rules name an identity for merges (this repo's App), `human` when merges run as the human's own login; when the rules call for `human` and the Setting says otherwise, ask the human to set it ([configure](../configure/SKILL.md)); never set it yourself. Read from the merge rule whether it requires a fresh review before an agent merges a PR (e.g. "an agent merges only a PR reviewed at its head"), and record it with `decide.py <run> set review_before_agent_merge yes|no`; the ticket PR's `## Merge` section states it. Then record the identity with `decide.py <run> set merge_identity <the Setting's value>` and, for `human`, `decide.py <run> set human <login>` with the human's GitHub login. `decisions.md` only records: each merge takes its identity from the Setting, and a recorded `merge_identity:` that differs refuses it (`wrong-identity`, nothing merges) rather than widening it. With `app`, an unset `identity_command` Setting or a token that is not an App installation's refuses every merge; with `human`, the login is whatever `gh api user` answers with the tokens unset (the tracker's human too), and a `[bot]` login, no login, or one other than a recorded `human:` (case aside) refuses it. Once `map.md` exists (now, when resuming; on a new run, at the end of step 4), run `setup.py <run>` (`OK run set up ci=<on|off> env=<path> skips=<n> [parallel=<n> (<cpus> cores, <gb> GB)]`): it runs `map.md`'s `Setup` once into `<run>/env/`, records `test_command:` (`map.md`'s `Checks` joined with `&&`, in that environment, which the merge scripts run them in too), `ci:` (`on` when a workflow on the base runs on pull requests into it and Actions are enabled), and `merge_identity:` and `human:` when `decisions.md` has none (a rerun never changes them), and lists in `skips.md` the tools the suite skipped without. It adds `parallel=<n>` only when no Level sets `max_parallel` (`settings list` shows it at Level `default`): the machine's default, `max(1, min(6, cpus - 2, GB // 4))` from its cores and memory (`BUILD_EPIC_MACHINE=<cpus>,<gb>` overrides the probe). **N** is then `--parallel N`, else `max_parallel` when a Level sets it, else that `parallel=`; until `setup.py` has run (steps 2-4 of a new run), the Setting's default. Tell the human N and its reason once: the flag, the Level that set `max_parallel`, or the machine (`N=4: 8 cores, 16 GB`). `FAIL run unclear-setup`: `map.md`'s `Setup` line is in no form it reads; have the planner fix it. `FAIL run setup-failed <command>`: tell the human with the log; a rerun tries `Setup` again. Then read `skips.md` and ask the human once, in one message, whether to install each tool it lists, and record the answer with `decide.py <run> quote "<their words>"`. Install the ones they accept as they say, then delete `skips.md` and run `setup.py <run>` again to list what is still skipped; a tool they decline stays skipped, and its reason reaches the ticket PR and the [Report](#report) under `Not exercised here`. Never ask again about a tool `decisions.md` already answers. Done when you know N and the merge rule, `run.md` exists and `decisions.md` holds `review_before_agent_merge:` and `merge_identity:` (and `human:` for `human`); once `map.md` exists, also `ci:` and `test_command:`, with every tool in `skips.md` asked about.

2. **Plan, pass A.** Start an `epic-planner` with these lines: `pass: A`, `input:` the epic (its link or ID; plain text goes in a file, given by path), `run:`, `notes:` the notes file path, `explore: always` when `--explore` was given, and `report: <run>/reports/plan-A.md`. Done when it reports `done` and `spec.md` and `areas.md` exist. On `blocked` (for example, no connector for the tracker), relay its `why` to the human and stop.

3. **Explore.** Skip this step when `areas.md` says `no exploration needed`. Otherwise start one `epic-explorer` per area, filling free slots, with these lines: `areas: <run>/areas.md`, `area:` its slug, `spec: <run>/spec.md`, `note: <run>/notes/<area>.md` and `report: <run>/reports/explore-<area>.md`. Done when every area has a note.

4. **Plan, pass B.** Start a fresh `epic-planner` with these lines: `pass: B`, `run:`, `notes:` and `report: <run>/reports/plan-B.md`. Done when `map.md`, `tickets/` and `tasks/` exist, every ticket and task is `ready`, and `python3 ~/.agents/skills/build-epic/plan_check.py <run>` prints `plan ok`; when it prints problems, write its output to `<run>/logs/plan-check.log` and start an `epic-planner` with `pass: revise`, `run:`, `notes:`, `reason:` that file's path and `report: <run>/reports/plan-revise-<n>.md`, `<n>` counting the run's revise passes from 1. Then finish step 1: run `setup.py <run>` and ask about `skips.md`'s tools as it says, before step 5 shows the plan.

5. **Approve.** Run `tracker_cmd.py <run> claims`: it sets each ticket whose issue is **claimed** by someone else to `claimed`. List every **leave-for-human clause** in the repo's rules from step 1: each rule that keeps an action for a human (an approval, a merge, a push to a protected branch, an approval-tier path in `.review-gate.yml` or `CODEOWNERS`), quoted. Run `guard_rules.py <run>`: it prints `rule <name> <kind> <pattern>` for each rule of the repo's merge guard (the changes no agent merge may land unless waived; format in [merge-guard.md](merge-guard.md)), and nothing when the repo has none. Each rule is one more leave-for-human clause: its clause is the rule name, copied as printed, shown with its kind and pattern. When the repo has a block, or a task's `Writes` adds one, list the built-in clause `merge-guard` too, which `guard_rules.py` does not print: a diff that changes the rules block itself. Without a `yes` for it, every task or ticket that edits the block is refused. `FAIL run bad-rule: <line>` means the repo's rules are unreadable and every merge will refuse: tell the human with the line. Show the human: each ticket (number, issues, title, blocked by, and who claimed it) with its tasks under it (number, title, blocked by, check); `map.md`'s `Lanes`, as the blocker graph of tickets in a short indented tree, one branch per lane; the **approval cost**: how many ticket PRs the merge rule from step 1 leaves to a human (e.g. ones touching an approval-tier path), and which tickets wait on those merges before they can start; with a base other than the default branch, ticket PRs into it merge without the repo's gate (`ship_ticket.py` runs `map.md`'s Checks first), so name instead the one gated PR left to the human after the run: the base into the default branch, and the approval-tier paths it will carry; the **gaps** (tasks whose check is not an automated test, plus `map.md`'s `Gaps` section); each of `spec.md`'s `Open questions` with the answer the planner assumed; the paths to `spec.md` and `map.md`; and the **Authorizations**, asked as [Asking for authorizations](#asking-for-authorizations) says. Wait for the answer. Ask for each clause's answer once, and record it with `decide.py <run> clause "<clause>" yes|no|ask "<the human's words>"` (for a guard rule, `decide.py <run> clause "<rule name>" ...`: only `yes` lets a merge carry its hits). From then on, record every verbatim decision the human gives about the run's rules (here or later in the run) with `decide.py <run> quote "<their words>"`, and never ask again what `decisions.md` already answers. Set each ticket the human takes to `ready` and each one they leave to someone else to `claimed`. On a rejection, write the human's words verbatim to `<run>/logs/rejection-<n>.md` and start an `epic-planner` with `pass: revise`, `run:`, `notes:`, `reason:` that file and `report: <run>/reports/plan-revise-<n>.md`, then show the plan again. Once approved, write `plan/TT.md` for each ticket the answer decided something about and mark every ticket's issue **planned** (see [Tracker](#tracker)). Done when the human approves, every clause has its row in `decisions.md`, and `tracker_cmd.py <run> planned` prints `OK`.

6. **Build.** Run `status.py <run>` to see what is ready, then repeat until done:
   - **Start** each `ready` ticket whose `Blocked by` tickets are all `merged`: `start_ticket.py <run> <TT>` makes its branch (its `Branch` line) from the run's base, here, where its tasks merge, and on origin, sets it `building` and marks its issue **started** (`OK TT building branch=<b> base=<sha7>`; see [Tracker](#tracker) for `started=manual`). `FAIL TT push` leaves it `ready`. A ticket blocked by a `claimed` or `in-review` one waits for that PR to merge.
   - **Dispatch** each `ready` task of a `building` ticket whose task blockers are all `done`, whose `ticket NN` blockers are all `merged`, and whose `Writes` share no path with any `in-progress` task's, while a slot is free: `start_task.py <run> <TT-NN>` adds `worktrees/TT-NN` on a new task branch from the ticket branch and sets the task `in-progress` (`OK TT-NN in-progress wt=<path> tip=<sha7>`). For a hub task (one with a `ticket NN` blocker) it also merges the run's base in, so the task edits the hub files on top of the tickets merged before it, and adds `synced=<sha7>`. When that merge conflicts it adds `conflict=<f1,f2,..>` and leaves the merge in the worktree, its markers in the files: the implementer resolves them first, so add `--sync <that value>` to its `task_prompt.py` call and run it here, never remotely. Its report is handled like any other; a `blocked` naming a hunk goes to the human, as under **On a report**. Then start an `epic-implementer` with the prompt `task_prompt.py <run> <TT-NN>` writes ([Subagents](#subagents); `--remote` when it runs remotely). A task you wrote yourself (a fix) has no `Writes` line and runs alone in its ticket.
   - **On a report**, whatever its status, once `report_check.py <run> <TT-NN>` printed `OK` (the report is at `reports/<TT-NN>.md`), first, for a subagent that ran here, run `capped stop <run>/worktrees/<TT-NN>` to end any test it left running; then run `finish_task.py <run> <TT-NN> --title "<the task's title in the commit convention>"`. It reads the report's status, commits what the subagent left uncommitted (a remote run's changes), merges the ticket branch in, and appends every changed path outside the task's `Writes` to that line, so the next Dispatch sees the real write set.
     - `OK TT-NN committed files=<n>`: when the task's file says `Tier: high`, **Review** it; then **Merge** it.
     - `OK TT-NN no-change`: the task is `done`, its worktree and branch removed, with no PR.
     - `FAIL TT-NN conflict <files>`: the merge is left in the worktree, its markers in the files. Send the task back to resolve them with a **resolver**: its `epic-implementer`, the prompt `task_prompt.py <run> <TT-NN> --resolve "<files>"` writes (its `resolve: <files>` line on top of the Dispatch prompt) and the description `resolve: TT-NN`. With remote on (as for an implementer, [Subagents](#subagents)), dispatch it remotely on `<run>/worktrees/TT-NN`, named `TT-NN-<slug>` as before, as [A resolver](../remote-subagents/SKILL.md#a-resolver) says: on exit 0, never commit its patch yourself. When a conflicted file has no `<<<<<<<` line or is missing (a modify/delete, rename or binary conflict), or the run exits 3 (the markers are still there), resolve it with a local resolver instead, as that section says. With remote off, continue the same implementer if your harness can, otherwise start a new one on the same worktree, here. The resolver's report is handled like any implementer's: it lands at `reports/TT-NN.md` (a local one writes it there through its `report:` line, a remote one's is `remote-agent`'s stdout, sent there as in [Subagents](#subagents)), and `report_check.py <run> <TT-NN>` (`--from-report` for a remote one) checks its block. Then run `finish_task.py <run> <TT-NN> --report <run>/reports/TT-NN.md --title "<as before>"`: it reads the resolver's status, commits the merge, with both parents, once no marker is left, and fails `conflict <files>` again while one is, or with the resolver's `blocked` or `plan-wrong` (see below).
     - `FAIL TT-NN blocked <why>` or `FAIL TT-NN plan-wrong <why>`: its changes are committed and nothing else touched; see **On `blocked`** and **On `plan-wrong`**.
   - **Review** a task before its Merge only when its file says `Tier: high`: every other task, a hub task included, is covered by its ticket's one deep review in step 7. The task has no PR, so the review runs here, from its worktree: follow [review-pr](../review-pr/SKILL.md) steps 3 and 4 with its prompt rendered by `python3 -I ~/.agents/skills/review-pr/scripts/review_prompt.py task --worktree <run>/worktrees/TT-NN --head <the worktree's HEAD> --base <ticket-branch> --run <run> --task <task file> --report <run>/reviews/TT-NN-<sha7>.md` (no `--pr`), the default reviewer only, its description `review: TT-NN`. Post nothing now: step 7 posts the report on the ticket PR. Sort its confirmed and plausible findings as step 7 does. Each **Fix** goes back to the task's implementer as a `red` does (below), numbered in `<run>/reviews/TT-NN-<sha7>-findings.md`; on its report, run `finish_task.py`, then review the new head the same way before the Merge. When a review still finds a Fix after the second round, stop and tell the human with the report's path. Each **Follow up** stays in the review's report.
   - **Merge** tasks one at a time per ticket, and merges into different tickets at once: `merge_task.py <run> <TT-NN>`. The scripts lock the repo only for the git commands that change shared metadata, never across a wait. In the task's worktree it catches up with the ticket branch, runs the merge guard and every command in `map.md`'s `Checks`, timing each suite (the task's proof until its ticket's deep review), then merges the task into the local ticket branch as one merge commit: no PR and no GitHub call. Once the ticket has a PR (a fix round after step 7 opened it), it also pushes the ticket branch, so the PR shows the fix. Then it sets the task `done`, removes its worktree and branch, and prints `OK TT-NN done suites=<n> <secs>s commit=<sha7>`, or one of these, each leaving the task `in-progress`:
     - `unreviewed`: a `Tier: high` task with no review of its head in `reviews/TT-NN-<sha7>.md`; **Review** it first.
     - `conflict <files>`: the catch-up merge was aborted. Run `finish_task.py` to start it again in the worktree (`FAIL TT-NN conflict <files>`), resolve it as **On a report** says (the remote resolver with remote on), then run `finish_task.py` once more and `merge_task.py` again; its guard still judges the resolved merge.
     - `red <suite>`: send the task back to its implementer with the failure from the log (continue the same subagent if your harness can, otherwise start a new one on the same worktree with the prompt `task_prompt.py <run> <TT-NN> --failure <log>` writes; remotely, always that prompt, with `--remote`). On its report, run `finish_task.py` as above, then merge again.
     - `ticket-moved`: another merge into the ticket landed first; run `merge_task.py` again.
     - `push`: the ticket branch would not push to its PR; the log says why. Run `merge_task.py` again (it does not merge twice); tell the human when it fails again.
     - `guarded <file:line rule>; ...`: the merge guard found changes hitting leave-for-human rules the human did not waive; nothing merged. Tell the human with the line, as printed. Never waive a rule yourself: only their answer, recorded with `decide.py <run> clause "<rule name>" yes "<their words>"`, waives it; otherwise the change must leave the task. `bad-rule`, `guard-no-base` and `git-<cmd>` mean the guard could not run; tell the human with the log.

     Add each `follow-up` of the task's report as an acceptance criterion to the not-yet-started task of the same ticket it concerns, or, when none fits, keep it for that ticket's review-fixes task in step 7.
   - **On `blocked`**, a remote task (a `blocked` report or a failed run) whose `remote-agent result <TT-NN-slug>` says `killed` gets one retry first: dispatch it again on the same worktree with the prompt `task_prompt.py <run> <TT-NN> --remote --cap "<kind> killed <cmd> (--mb <mb> --secs <secs>)"` writes: its one **cap note** line, from that result's last `capped_kills` entry and its `caps`. When the prompt of the run that ended already carried a `cap:` line, there is no second retry: set the task `blocked` with that note as its `why`. Otherwise, set the task to `blocked`, run `tracker_cmd.py <run> blocked <TT-NN> "<why>"`, and keep dispatching the rest.
   - **On `plan-wrong`**: run `tracker_cmd.py <run> blocked <TT-NN> "<why>"`, stop dispatching and let running implementers finish. Start an `epic-planner` with `pass: revise`, `run:`, `notes:`, `reason:` the task's path and its report file `<run>/reports/<TT-NN>.md`, and `report: <run>/reports/plan-revise-<n>.md`. Show the human its changed tickets and tasks as in step 5 and wait for approval, run `tracker_cmd.py <run> planned` and `tracker_cmd.py <run> unblocked <TT>`, then resume dispatching.
   - **Base change**: when the human asks to move the run onto another base mid-run, run `catch_up.py <run> <new-base>` first. It changes nothing and prints `OK run catch-up <n> unstarted <m> started unstarted=<TT,..|none> started=<TT,..|none>`: the unstarted tickets `start_ticket.py` will cut from the new base, and the started ones whose branch lacks its tip. Offer the human that catch-up with both lists as printed, and record their answer with `decide.py <run> quote`. Once they accept, run `catch_up.py <run> <new-base> --apply`: it records `base:`, merges the new base into each started ticket's branch that lacks it and pushes it, then moves every started ticket's open PR still on another base to the new base (`OK run caught-up base=<new-base> ...`). `FAIL run conflict <TT>: <files>` leaves those branches and their PRs as they were: hand the files to the human, then run it again. On `FAIL run pr-edit <TT>`, run it again: a rerun moves any PR still on the old base. `FAIL run no-base <new-base>` records nothing: the branch is not on origin.
   - **Tell the human** only when a ticket ships (step 7) or they must decide something (a `blocked` or `plan-wrong` task, a `FAIL` this file says to tell them about, a re-plan to approve): `status.py <run> --line <TT>` for the ticket concerned, as printed, then the question in one sentence and the path of the report or log that holds the details. Nothing else goes to them while the build runs.
   - **Ship** each `building` ticket whose tasks are all `done`, by step 7.

   Done when `status.py <run>` shows every ticket you build `merged` or `in-review`. When the only ones left are `blocked`, or wait on a `blocked`, `claimed` or `in-review` ticket, report to the human and stop: each ticket branch keeps every merged task, and a later run resumes from there.

7. **Ship a ticket.** Run `ship_ticket.py <run> <TT> open`. You write no part of the PR: the script generates its body from the run folder alone (every `## ` section of the repo's PR template filled from the ticket, its tasks, `decisions.md` and `reports/*.checks.json`; then the tasks with their merge commits and acceptance criteria, `## Not exercised here`, `## Merge` and `Closes #n`), pushes the ticket branch (its tasks' merge commits, on this machine until now), puts the ticket's worktree `worktrees/TT` at its tip and opens the ticket PR into the base, recording it as the ticket's `PR:` line (`OK TT open pr=<n>`; a rerun edits that PR). `FAIL TT push`: origin refused the ticket branch; tell the human with the log. `FAIL TT empty-template-section <sections>` sends nothing: the run has nothing for those headings. `Testing` fails when no task of the ticket saved a `reports/*.checks.json` (its merges did not run `merge_task.py`); any other section when neither the run nor the ticket file has anything for that heading. Tell the human with the line and the log; never write the section yourself. Then the ticket's one deep review, which covers all its tasks, its hub task included: follow [review-pr](../review-pr/SKILL.md) steps 1-5 on the ticket PR with `--mode ticket --run <run> --base origin/<the run's base> --task <ticket file>`: the default reviewer, plus the security reviewer only when the ticket's tier is `high`. Each reviewer runs remotely or here as in step 6 (a remote one's `result.json` written to `<run>/remote/`, [Subagents](#subagents)) and saves its report to `<run>/reviews/<PR>-<sha7>.md` (the security reviewer's ends `-security.md`; a remote one's copied there from its run), and review-pr's step 5 posts each here with `post_review.py <run> <PR> <report-file> --base origin/<the run's base> [--note <text>]`: a one-line header naming the PR and head the report's name records, the report's bytes, then your note of dropped and plausible findings. There are no inline comments: findings cite `path:line` in the report. It prints `OK PR<n> review <url>`; `empty-review` means the file is missing or blank, `bad-report` that it is not UTF-8. On `FAIL PR<n> post-denied <report path>` (GitHub refused the review), or when your harness denies running `post_review.py`, do not retry: the findings stay in that report file, and the run's report names its path once. Once the deep review is posted, post each review step 6 ran on a `Tier: high` task of the ticket, last one per task: `post_review.py <run> <PR> <run>/reviews/TT-NN-<sha7>.md --base <ticket-branch>` (its header names the task and the head it reviewed before it merged); always after the deep review, which must be the first review on the PR. Sort the confirmed and plausible findings against the ticket's acceptance criteria (its tasks' `Acceptance criteria`) and the merge rule:
   - **Fix**: a `blocker`, or a `should-fix` that breaks an acceptance criterion or a written rule of the repo.
   - **Follow up**: everything else, hardening beyond the criteria included. Each stays a row of the review's `## Follow-ups` section, where the human reads it; nothing records it elsewhere.

   When any finding is **Fix**, or step 6 kept an implementer `follow-up` for this ticket, write them as one new task `tasks/TT-NN-review-fixes.md` (each finding or follow-up an acceptance criterion quoted from its source, its scenario the check) and number its **Fix** findings in `<run>/reviews/<PR>-<sha7>-findings.md` (the reviewed PR and head). Run the task through step 6 (reviewed there only when its file says `Tier: high`): its merge pushes the ticket branch, so the ticket PR shows the fix. Then a `re-review` on the ticket PR checks it: review-pr steps 1-5 with `--mode re-review --run <run> --base <the head reviewed> --findings <that file>`. When it still finds a Fix after the second round, stop and tell the human with the report's path. That task is the ticket's one fix round; its checks and its re-review are its proof. With nothing to fix, go straight on. Then run `ship_ticket.py <run> <TT> merge [--reviewed <sha>]`: it pushes the ticket branch and merges the PR at its tip by the merge rule, closes the ticket's issues when the PR's base is the default branch (into an integration branch it labels them `merged-to-<base>` and leaves them open), and removes the ticket's worktree. Into an integration branch, it first runs `map.md`'s Checks on the ticket head, since the repo's gate judges only PRs into the default branch, and merges only when the ticket's tree is the reviewed tree. The reviewed head is the commit the ticket PR's review was posted on (`<run>/logs/PR<n>-review.json`); `--reviewed <sha>` overrides it. `OK TT merged pr=<n>` sets the ticket `merged`; `OK TT in-review pr=<n>` means the `merge_command` rule answered that the merge waits on a human's approval, and the ticket is `in-review`. On `FAIL TT head-moved`, run it again; on `FAIL TT merge` or `FAIL TT push`, tell the human with the log; on `FAIL TT no-merge-rule`, the repo gates the default branch and `merge_command` is unset: ask the human to set it, then run it again. These refuse and merge nothing: `FAIL TT no-review` (no `--reviewed` and no saved review: post the ticket's review), `reviewed-unknown` (git does not know the reviewed head: check the SHA), `red <suite>` (a Check failed on the ticket head: hand it to a fix task as in step 6), `tree-mismatch` (the ticket branch changed since the review: review its head again), `wrong-base <branch>` (the PR targets another branch than the run's base), and `guarded <file:line rule>; ...` with the guard's other failures (as in step 6: tell the human with the line, and never waive a rule yourself); tell the human with the log for any but the first. 

   Then run `tracker_cmd.py <run> close-epic` and `status.py <run> --write`, and give the human the line `status.py <run> --line <TT>` prints, as printed. Continue from `state.md`, not from the turns before it: where your harness can compact or clear your context, do it now, keeping only the run folder's path and this step; otherwise read `state.md` and act on it alone. Done when the ticket is `merged` or `in-review` and `state.md` is written.

8. **Clean up.** Run `clean.py <run>` once no task is `in-progress` (it refuses while one is): it removes every worktree under `worktrees/` and the run's local task branches, and the `in progress` and `blocked` labels from the issues the run closed (`OK run clean <n> removed`). Keep the run folder.

### Asking for authorizations

A clause quoted from a rules file is hard to judge: it names paths and calls, not what the run will do. Ask about each one so the human can answer without opening anything:

1. Number each clause, and give it a plain name of a few words ("Changes to the tests folder").
2. **Guards:** one sentence, in your own words, on what it keeps for the human and the risk behind it ("test code runs on this machine when the checks run").
3. **This run:** which tickets or tasks will hit it, judged from their `Writes` lines and the spec, or "not expected". Then what each answer means for those: `yes`, agents merge them on their own; `no`, each one stops until the human merges it, and every ticket behind it waits too; `ask`, the run pauses at each hit and asks.
4. **Recommended:** your answer and the one reason for it.
5. **Rule:** the clause quoted word for word, last, on its own line; for a guard rule, its name, kind and pattern as `guard_rules.py` printed them.

Put the clauses this run is not expected to hit together at the end, under "Not expected to come up", with one recommended answer for all of them. Close with one line the human can copy and edit as their reply, such as `1 yes, 2 ask, 3 yes`. Say that the answers hold for this run only.

## Report

Run `status.py <run> --write` once more. Give one line per ticket from `status.py <run> --line <TT>`, as printed (its state, PR and what it waits on: **merged**, **waiting** and on whom, or not started and why), then `status.py <run> --report` as printed: the table, each task with its final status, then, when any ticket saved a skip reason, its `## Not exercised here` section, the skipped tests by ticket. Add every `blocked` task with its `why`, every `claimed` ticket with who claimed it, every ticket merged into an integration branch, with the line `Issues #<a>, ... are labelled merged-to-<base> and close when <base> reaches <default branch>.`, then the one PR left to the human: `<base>` into `<default branch>`, the repo's gate judging it and its approval-tier paths needing the human's approval, and the run folder's path. Then list the path of every report under `reports/` and `reviews/` that holds a `## Follow-ups` section, one per line: the work left out, the feature interactions and each owner-only file's ready-to-apply patch are there. Never retell, sort or file them yourself. When posting a review was denied, say once where its findings are kept: the report path from the `post-denied` line, one line per PR. Say whether `tracker_cmd.py <run> close-epic` closed the epic, or which issues keep it open. With `ci: off`, say that the local `Checks` runs were the only proof.
