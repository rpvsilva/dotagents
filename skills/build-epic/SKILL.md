Build an epic as **tickets** made of **tasks**. A ticket is one tracker issue: its own branch `feat/<ticket-slug>` and one PR into the default branch, so several developers can split an epic by ticket. A task is one implementer's slice of a ticket: its own branch and one PR into the ticket branch, so every change leaves a trail on the tracker. A ticket whose suites are **slow** gets one **tuning task** after its last implementer task: a test-tuner's own branch and PR into the ticket branch, making the tests the ticket touched faster and better covered.

Work runs in **lanes** ([planner-brief.md](planner-brief.md) pass B): tickets that share files run one after another, and only lanes with disjoint write sets run in parallel. A run that fills fewer slots and merges cleanly beats one that fills them all and spends its runs on conflicts.

You are the **orchestrator**: you start subagents, run the [step scripts](#step-scripts) that track statuses and open and merge PRs, and talk to the human. Keep your context **thin**: you read the run folder's short files (ticket and task headers, the `Checks` section of `map.md`, reports), not the code or the tracker; the one exception is verifying review findings in step 7. Every heavy read happens in a subagent that writes its result to a file and returns a short report.

Input: an epic or issue (link or ID, on any tracker), or plain text. Optional: `--parallel N`; `--explore` to always run the explorers.

## Run folder

`~/.agents/runs/<repo>/<epic-slug>/`: `<repo>` is the repo folder's name, `<epic-slug>` the tracker ID plus a few words (`gh-12-due-dates`). It holds:

- `run.md`: the repo's path, its default branch, its remote and the run's identity (`Repo:`, `Default:`, `Remote:`, `Identity:`), and the epic's issue when it has one (`Epic:`), written by `init_run.py` in step 1. Every step script reads it, never the current folder.
- `spec.md`, `areas.md`, `notes/<area>.md`, `map.md`: written by the planner and explorers.
- `tickets/TT-<slug>.md`: one per ticket. Its `Status:` line is `ready`, `claimed` (another developer builds it), `building`, `in-review` (its PR waits on a human), `merged` or `blocked`. The step scripts add its `PR:` line (the draft PR `merge_task.py` opens, or the one `ship_ticket.py open` opens), its `CI red:` line (the last red Ticket CI run reported) and its `Claimed by:` line (`tracker_cmd.py claims`).
- `tasks/TT-NN-<slug>.md`: one per task, `TT` its ticket. Its `Status:` line is `ready`, `in-progress`, `done` (its PR is merged) or `blocked`. `open_pr.py` adds its `PR:` line; `finish_task.py` appends to its `Writes` line every path it changed outside it.
- `tasks/TT-tests.md`: the ticket's tuning task, written by `merge_task.py` (step 6): a title, `Status:`, and `Range: <ticket branch's first commit>..<tip>`, the commits its tasks added.
- `plan/TT.md`: what you decided for a ticket at approval (the answers to `spec.md`'s open questions that bear on it, any change to its scope), put on its issue by `tracker_cmd.py planned`.
- `logs/<id>-<step>.log`: every git, gh and test output of a step script, named on its `FAIL` line; beside them, the PR bodies (`<id>-pr-body.md`) and review payloads (`PR<n>-review.json`) the scripts sent.
- `reports/<id>.md`: each implementer's report (`finish_task.py --report`), and `reports/<id>.checks.json`: each suite `merge_task.py` ran, with its time and result.
- `tracker.json`: the run's identity, the human's login, the labels created and the tracker updates held while the identity was away (`steplib/tracker.py`).
- `decisions.md`, when present: the run's decisions; `ci: off` turns Ticket CI off.
- `followups.md`: work found but left out of the build (review findings outside a ticket's acceptance criteria), one line each with its ticket. You write it.
- `worktrees/TT-NN/` and `worktrees/TT-tests/` (one per task being built, from `start_task.py`) and `worktrees/TT/` (one per ticket being shipped, from `ship_ticket.py open`).
- `dispatcher.sha` and `worktrees/dispatcher/`: the pinned dispatcher, only when the epic changes the dispatcher's own repo (`pin_dispatcher.py`, see [Remote dispatcher](#remote-dispatcher)).

Only the step scripts and you change `Status:` and `PR:` lines; subagents leave them alone.

When the folder already exists, **resume**: run `resume.py <run>`. It sets each `in-review` ticket whose PR merged to `merged`, sends every `in-progress` task with no PR back to `ready` (worktree and branch removed), finishes every task whose PR merged but is not yet `done` (opening the ticket's draft PR when it has none), leaves every task with an open PR for **Merge** in step 6, and keeps a pinned dispatcher at its `dispatcher.sha`. Then run `status.py <run>` and continue at the first step whose done-condition is not met.

### Step scripts

Every routine git and gh step is one command: `python3 -I ~/.agents/skills/build-epic/scripts/<step>.py <run> <id> [...]`, written below as `<step>.py <run> ...`. Each works from any folder, prints one line, `OK <id> <state> [details]` or `FAIL <id> <reason> (log: <path>)`, and exits non-zero on `FAIL`. Act on that line; open the log only to understand a `FAIL` or to hand it to a subagent. Never compose the git or gh commands a script runs yourself: when a step fails in a way this file does not cover, tell the human with the log path. Transient GitHub failures are retried by the scripts (waits of 2, 4, 8 and 16 s, scaled by `BUILD_EPIC_RETRY_SLEEP`, which tests set to 0). Every `gh` call a script makes, for PRs and the tracker alike, and the merge rule it runs, act as the run's **identity**: `run.md`'s `Identity:` line. When it names a command (the `identity_command` Setting, e.g. this repo's `scripts/gh-app-token.sh`), each call gets a fresh token from it, so no wait (a long Ticket CI one included) outlives the token, and `FAIL <id> identity-token` means the command failed. `Identity: login` acts as the current `gh` login. `status.py <run>` is the one that prints a table: one line per ticket, its tasks under it, with status, PR, blockers and title.

## Subagents

| Agent | Brief | Writes |
|---|---|---|
| `epic-planner` | [planner-brief.md](planner-brief.md) | `spec.md`, `areas.md`, `map.md`, `tickets/`, `tasks/` |
| `epic-explorer` | [explorer-brief.md](explorer-brief.md) | `notes/<area>.md` |
| `epic-implementer` | [implementer-brief.md](implementer-brief.md) | commits on its task branch |
| `test-tuner` | [tuner-brief.md](../tune-tests/tuner-brief.md) | commits on its tuning task's branch |

Start and limit them as in [Subagents](../_shared/conventions.md#subagents): at most **N** at once (the **slots**).

The `epic-implementer` and `test-tuner` are **remote-capable** ([Remote subagents](../_shared/conventions.md#remote-subagents)): name each after its task's file, `--name TT-NN-<slug>`, and attach its task, `spec.md`, `map.md` and `notes/`. Dispatch it with the command [Remote dispatcher](#remote-dispatcher) names. Act on its exit code as that section's step 4 says, except the commit: a remote run leaves its changes uncommitted, and `finish_task.py` (step 6, **On a report**) commits them and catches the task up with the ticket branch. The planner and explorers write into the run folder, so they always run here.

Every subagent ends with this report, and you act on it alone:

```
status: done | blocked | plan-wrong
changed: <paths, or the last commit SHA>
why: <one line, when status is not done>
follow-up: <optional, implementers only: work a later task must pick up>
```

The `test-tuner` reports `done` or `blocked`, with its `time`, `covered`, `moved` and `left` lines on top; they go in its PR's body.

### Remote dispatcher

The remote dispatcher is `~/.agents/bin/remote-agent`, a link into the checkout that installed it. When the epic changes that same repo, merges during the epic would change the dispatcher under the running tasks, so dispatch from a pinned copy instead. In step 1, run `pin_dispatcher.py <run>`:

- `OK dispatcher installed`: the link is missing or points into another checkout. Dispatch with `~/.agents/bin/remote-agent`.
- `OK dispatcher pinned <sha7>`: the link points into the epic's repo. The script wrote the default branch's tip into `<run>/dispatcher.sha` once per run and keeps `<run>/worktrees/dispatcher` detached at it (re-created when gone, never moved to a newer commit; `resume.py` keeps it too). Dispatch every remote run with `<run>/worktrees/dispatcher/scripts/remote-agent.sh` in place of `~/.agents/bin/remote-agent`, with the same arguments. It finds its sibling scripts from its own path, so it runs the pinned code. The pinned copy may predate features the epic adds; rely only on what it already does.

The pin covers the scripts only. The pinned `remote-agent.sh` still packs the sandbox's setup from `~/.agents` and `~/.claude` on this machine, following their links into the installed checkout, so remote runs get that checkout's working tree: neither the pinned commit nor the epic's branches. An epic that changes hooks, skills or briefs is therefore built under the installed versions; its changes reach remote runs only once the installed checkout holds them. Keep that checkout where it is during the epic (no pulls, no switching branches), so every task runs under the same setup.

## Tracker

Keep the tracker in step with the build. Each ticket's `Issue` line names its issues, and every update below applies to each of them; with plain-text input there is none, and you skip this. The scripts make every GitHub update as the run's identity ([Step scripts](#step-scripts)), each only while the active login is still the one (the login of its first update, kept in `tracker.json`). When another session switched accounts, the update is held and the script fails `identity-changed`: keep building, and ask the human to switch back. Once they have, `tracker_cmd.py <run> flush` applies the held updates in order (every later tracker update applies them first too).

When the `tracker` Setting names another tracker, `tracker_cmd.py` touches nothing and its line ends `manual tracker=<name>`, and `start_ticket.py` adds `started=manual`: make that update yourself through the tracker's connector, as the bullet says.

- **Claimed**: an issue assigned to anyone but the human you work for belongs to another developer. `tracker_cmd.py <run> claims` (step 5) sets each `ready` ticket with such an issue to `claimed` and writes who on its `Claimed by:` line. `start_ticket.py` claims each ticket you start by assigning its issues to the human.
- **Planned**, once the human approves the plan (step 5) and again after each approved re-plan: first write `<run>/plan/TT.md` for each ticket the approval decided something about (the answers decided for `spec.md`'s open questions that bear on it, any change to its scope or acceptance criteria), then run `tracker_cmd.py <run> planned`. It puts one comment on every ticket's issue, claimed ones included, starting with the marker `<!-- build-epic-plan -->`: `plan/TT.md`, then the ticket's tasks (number, title, blocked by). An issue that already holds a marked comment has it edited, so each issue carries one current plan. `map.md` stays out: it is for implementers.
- **Started**, when a ticket starts: `start_ticket.py` adds the `in progress` label (created once per run) and assigns each issue to the human. With `started=manual` on its line (the `in_progress` Setting is set, e.g. a GitHub Projects status field, or the `tracker` Setting names another tracker), mark the issues started yourself as that Setting says.
- **Blocked**, when a task ends `blocked` or `plan-wrong`: `tracker_cmd.py <run> blocked <TT-NN> "<why>"` adds the `blocked` label to its ticket's issues and one comment, `Blocked: task TT-NN (<title>): <why>`. Once a re-plan or fix lets the task run again, `tracker_cmd.py <run> unblocked <TT>` removes the label.
- **Done** belongs to the ticket PR's merge: `ship_ticket.py <run> <TT> merge` closes the ticket's issues when the PR's own base (its `baseRefName` on GitHub) is the default branch. Into any other base the issues stay open; say so in the report.
- **Epic done**: after each ticket ships, run `tracker_cmd.py <run> close-epic`. It closes the epic's issue (`run.md`'s `Epic:` line, or give its number) once every ticket's issue is closed (`OK epic closed #<n>`); until then it names the ones still open (`OK epic open #<a> ...`) and changes nothing.

## Steps

1. **Set up.** [Learn the rules](../_shared/conventions.md#learn-the-rules) with notes file `.agents/build-epic-notes.md` (test commands, areas to avoid) and the `tracker`, `max_parallel`, `in_progress`, `tune_min_seconds`, `merge_command` and `identity_command` Settings, and the [ship-pr](../ship-pr/SKILL.md) rules from its step 1: commit convention, merge rule and the identity PRs are opened and merged as. When the merge rule is a command (this repo's `scripts/merge-pr.sh`), it belongs in the `merge_command` Setting, so the scripts merge by it, task and ticket PRs alike: when that Setting is unset, ask the human to set it ([configure](../configure/SKILL.md)); a repo with a `.review-gate.yml` refuses ticket merges into the default branch without it. Likewise, when the rules name an identity (this repo's `GH_TOKEN="$(scripts/gh-app-token.sh)"`), its token command belongs in the `identity_command` Setting; unset, the scripts act as the current `gh` login. When the run folder exists, resume it (see [Run folder](#run-folder)); otherwise create it and run `init_run.py <run> <repo> [--epic <n>]`, `--epic` naming the epic's issue when the input is one (`OK run initialised repo=<path> default=<branch> remote=<url> identity=<command|login>`): the identity is decided here, once per run. When subagents run remotely, run `pin_dispatcher.py <run>` for the dispatch command ([Remote dispatcher](#remote-dispatcher)). Done when you know N, the merge rule and the dispatch command, and `run.md` exists.

2. **Plan, pass A.** Start an `epic-planner` with: pass `A`, the input, the run folder, the notes file path, and `explore: always` when `--explore` was given. Done when it reports `done` and `spec.md` and `areas.md` exist. On `blocked` (for example, no connector for the tracker), relay its `why` to the human and stop.

3. **Explore.** Skip this step when `areas.md` says `no exploration needed`. Otherwise start one `epic-explorer` per area, filling free slots: the area's name, question and starting paths, the `spec.md` path, and `notes/<area>.md` as its output. Done when every area has a note.

4. **Plan, pass B.** Start a fresh `epic-planner` with: pass `B`, the run folder, the notes file path. Done when `map.md`, `tickets/` and `tasks/` exist, every ticket and task is `ready`, and `python3 ~/.agents/skills/build-epic/plan_check.py <run>` prints `plan ok`; when it prints problems, start an `epic-planner` with pass `revise` and its output as the reason.

5. **Approve.** Run `tracker_cmd.py <run> claims`: it sets each ticket whose issue is **claimed** by someone else to `claimed`. Show the human: each ticket (number, issues, title, blocked by, and who claimed it) with its tasks under it (number, title, blocked by, check); `map.md`'s `Lanes`, as the blocker graph of tickets in a short indented tree, one branch per lane; the **approval cost**: how many ticket PRs the merge rule from step 1 leaves to a human (e.g. ones touching an approval-tier path), and which tickets wait on those merges before they can start; the **gaps** (tasks whose check is not an automated test, plus `map.md`'s `Gaps` section); each of `spec.md`'s `Open questions` with the answer the planner assumed; and the paths to `spec.md` and `map.md`. Wait for the answer. Set each ticket the human takes to `ready` and each one they leave to someone else to `claimed`. On a rejection, start an `epic-planner` with pass `revise` and the human's words verbatim, then show the plan again. Once approved, write `plan/TT.md` for each ticket the answer decided something about and mark every ticket's issue **planned** (see [Tracker](#tracker)). Done when the human approves and `tracker_cmd.py <run> planned` prints `OK`.

6. **Build.** Run `status.py <run>` to see what is ready, then repeat until done:
   - **Start** each `ready` ticket whose `Blocked by` tickets are all `merged`: `start_ticket.py <run> <TT>` pushes its branch (its `Branch` line) from the default branch, sets it `building` and marks its issue **started** (`OK TT building branch=<b> base=<sha7>`; see [Tracker](#tracker) for `started=manual`). `FAIL TT push` leaves it `ready`. A ticket blocked by a `claimed` or `in-review` one waits for that PR to merge.
   - **Dispatch** each `ready` task of a `building` ticket whose task blockers are all `done`, whose `ticket NN` blockers are all `merged`, and whose `Writes` share no path with any `in-progress` task's, while a slot is free: `start_task.py <run> <TT-NN>` adds `worktrees/TT-NN` on a new task branch from the ticket branch and sets the task `in-progress` (`OK TT-NN in-progress wt=<path> tip=<sha7>`). For a hub task (one with a `ticket NN` blocker) it also merges the default branch in, so the task edits the hub files on top of the tickets merged before it, and adds `synced=<sha7>`; `FAIL TT-NN sync-conflict <files>` leaves the task `ready` with no worktree: hand the files to the human, or to a re-plan when a ticket's merge made them clash. Then start an `epic-implementer` with the task path, the run folder, the worktree path and `origin/<ticket-branch>`. A task you wrote yourself (tuning, fix) has no `Writes` line and runs alone in its ticket. A tuning task starts the same way (`start_task.py <run> <TT>-tests`, on `worktrees/TT-tests`), with a `test-tuner` given the worktree path, its `Range` as the scope and the notes file path; it measures its own baseline.
   - **On a report**, whatever its status, write it to a file and run `finish_task.py <run> <TT-NN> --report <file> --title "<the task's title in the commit convention>"`. It copies the report to `reports/<TT-NN>.md`, commits what the subagent left uncommitted (a remote run's changes), merges the ticket branch in, and appends every changed path outside the task's `Writes` to that line, so the next Dispatch sees the real write set.
     - `OK TT-NN committed files=<n>`: run `open_pr.py <run> <TT-NN>` (the first time) to push the branch and open its PR into the ticket branch, titled after its first commit, with a body naming what it builds, its check and result and `Part of #n` (`OK TT-NN pr=<n> <url>`, recorded as its `PR:` line). Then **Merge** it.
     - `OK TT-NN no-change`: the task is `done`, its worktree and branch removed, with no PR (e.g. a tuner that changed nothing).
     - `FAIL TT-NN conflict <files>`: the merge is left in the worktree; send the task back to resolve the markers, then run `finish_task.py` again, which commits the merge.
     - `FAIL TT-NN blocked <why>` or `FAIL TT-NN plan-wrong <why>`: its changes are committed and nothing else touched; see **On `blocked`** and **On `plan-wrong`**.

     For a tuning task, first **verify** it as [tune-tests](../tune-tests/SKILL.md) step 5 does, against the baseline in its report, sending what does not hold back to its tuner once; its title is `test: tune <the ticket's title>`: pass it to `open_pr.py <run> <TT>-tests --title "test: tune <the ticket's title>"`, since the tuner's first commit names something else.
   - **Merge** task PRs one at a time per ticket: `merge_task.py <run> <TT-NN>`. In the task's worktree it reads the ticket PR's checks first (**Ticket CI**), catches up with the ticket branch, runs every command in `map.md`'s `Checks`, timing each suite (CI runs only on PRs into the default branch, so this run is the task PR's check, and its proof until the ticket's one review in step 7), pushes, and merges by the `merge_command` Setting, run from the repo root with `{pr}` and `{sha}` filled in (unset: a squash merge pinned to the head it tested). Then it sets the task `done`, removes its worktree and branch, opens the ticket's draft PR when it has none, and, when this was the ticket's last implementer task and a suite ran at least `tune_min_seconds`, writes the tuning task `tasks/TT-tests.md`, `ready`. It prints `OK TT-NN done suites=<n> <secs>s`, or one of these, each but the last leaving the task `in-progress`:
     - `red <suite>` or `conflict <files>`: send the task back to its implementer with the failure from the log (continue the same subagent if your harness can, otherwise start a new one on the same worktree). On its report, run `finish_task.py` as above, then `push_fix.py <run> <TT-NN>` (`OK TT-NN pushed head=<sha7>`) in place of `open_pr.py`, and merge again.
     - `ticket-ci-red <run-id>`: see **Ticket CI**.
     - `head-moved`: the PR's head is not the commit the checks ran on; run `merge_task.py` again.
     - `merge` or `push`: the merge rule or the push refused; the log says why. Tell the human.
     - `ticket-pr`: the task is already `done` and merged, but the ticket's draft PR could not be opened. The next merge into the ticket, or `resume.py`, opens it.

     Add each `follow-up` of the task's report as an acceptance criterion to the not-yet-started task of the same ticket it concerns, or, when none fits, keep it for that ticket's review-fixes task in step 7.
   - **Ticket CI**, so CI runs before the ticket ships (it runs only on PRs into the default branch). `merge_task.py` opens the ticket's **draft** PR into the default branch after its first merge, titled by the commit convention and with `Part of #n`, and records it as the ticket's `PR:` line. Before each later merge it waits on that PR's pending checks (the previous merge's head), ignoring cancelled ones. On a red one it records the run on the ticket's `CI red:` line and fails `ticket-ci-red <run-id>` once per run id, its failed log in the step's log. Send that failure back: add it as an acceptance criterion to the ticket's next not-yet-started task; when none is left, write a fix task `tasks/TT-NN-fix-ci.md` with the failure as its check. Then run `merge_task.py` again: the same red run no longer stops it, so the next merge goes ahead and the fix lands. `decisions.md`'s `ci: off` turns Ticket CI off; a PR with no checks has nothing to wait on, and the Merge step's local `Checks` stand as the ticket's CI (tell the human once).
   - **On `blocked`**: set the task to `blocked`, run `tracker_cmd.py <run> blocked <TT-NN> "<why>"`, and keep dispatching the rest.
   - **On `plan-wrong`**: run `tracker_cmd.py <run> blocked <TT-NN> "<why>"`, stop dispatching and let running implementers finish. Start an `epic-planner` with pass `revise`, the task path and the implementer's `why`. Show the human its changed tickets and tasks as in step 5 and wait for approval, run `tracker_cmd.py <run> planned` and `tracker_cmd.py <run> unblocked <TT>`, then resume dispatching.
   - **Ship** each `building` ticket whose tasks are all `done`, by step 7.

   Done when `status.py <run>` shows every ticket you build `merged` or `in-review`. When the only ones left are `blocked`, or wait on a `blocked`, `claimed` or `in-review` ticket, report to the human and stop: each ticket branch keeps every merged task, and a later run resumes from there.

7. **Ship a ticket.** First write the ticket PR's body to a file: every section of the repo's PR template (`.github/pull_request_template.md` when there is one; in this repo `Summary`, `Testing`, `Risk` and `How to revert`) under its own `## ` heading, filled from the ticket, its task reports and `reports/*.checks.json` (under `Testing`, the checks that ran and their results). Leave out the task list and the closing references: the script adds them. Then `ship_ticket.py <run> <TT> open --body-file <file>` adds the ticket's worktree `worktrees/TT` and makes its PR ready for review into the base: the draft from step 6 gets the ticket's title and your body, then its tasks (title, PR link) and `Closes #n`; when step 6 opened none, it opens one and records it as the ticket's `PR:` line (`OK TT open pr=<n>`). `FAIL TT empty-template-section <sections>` names the template sections your body leaves empty, `TODO`, `N/A` or only unchecked boxes, and sends nothing: fill them and run it again. Then follow [review-pr](../review-pr/SKILL.md) steps 1-4 on the PR, the ticket's one review, and post its kept findings with `post_review.py <run> <PR> <report-file> [--comments <json>]` in place of review-pr's step 5 (`OK PR<n> review <url>`; `empty-review` means the file is missing or blank). Sort the kept findings against the ticket's acceptance criteria (its tasks' `Acceptance criteria`) and the merge rule:
   - **Fix**: a `blocker`, or a `should-fix` that breaks an acceptance criterion or a written rule of the repo.
   - **Follow up**: everything else, hardening beyond the criteria included. Add each to `followups.md`, one line with its ticket and the review's link.

   When any finding is **Fix**, or step 6 kept an implementer `follow-up` for this ticket, write them as one new task `tasks/TT-NN-review-fixes.md` (each finding or follow-up an acceptance criterion quoted from its source, its scenario the check) and run it through step 6; its merge updates the ticket PR. That task is the ticket's one fix round, and its checks are its proof. With nothing to fix, go straight on. Then run `ship_ticket.py <run> <TT> merge`: it merges the PR at the ticket branch's tip by the merge rule, closes the ticket's issues when the PR's base is the default branch, and removes the ticket's worktree. `OK TT merged pr=<n>` sets the ticket `merged`; `OK TT in-review pr=<n>` means the `merge_command` rule answered that the merge waits on a human's approval, and the ticket is `in-review`. On `FAIL TT head-moved`, run it again; on `FAIL TT merge`, tell the human with the log; on `FAIL TT no-merge-rule`, the repo gates the default branch and `merge_command` is unset: ask the human to set it, then run it again. Then run `tracker_cmd.py <run> close-epic` and `status.py <run>`, give the human one line for the ticket, and continue from that table. Done when the ticket is `merged` or `in-review`.

8. **Clean up.** Run `clean.py <run>` once no task is `in-progress` (it refuses while one is): it removes every worktree under `worktrees/` (`dispatcher/` included) and the run's local task branches, and the `in progress` and `blocked` labels from the issues the run closed (`OK run clean <n> removed`). Keep the run folder.

## Report

`status.py <run>` gives the lines: one per ticket with its PR URL and state (**merged**, **waiting** and on whom, or not started and why), then one per task with its final status. Add every `blocked` task with its `why`, every `claimed` ticket with who claimed it, every ticket merged into a base other than the default branch (its issues stay open until that base reaches the default branch), the count of lines in `followups.md`, and the run folder's path. Say whether `tracker_cmd.py <run> close-epic` closed the epic, or which issues keep it open.
