---
name: review-pr
description: First-pass PR review by fresh subagents, at the depth the change's risk tier calls for (a security reviewer only on high tier); each reviewer's own report posted as a comment-only review, with your verification as a note.
disable-model-invocation: true
---

Give a PR its first review before a human looks: a fresh reviewer finds problems and saves its report, you **verify** each finding, and the report is posted as the reviewer wrote it, with your verdicts in a note under it. The review is always comment-only: approval belongs to a human.

Input: the PR number. Optional: `--dry-run` to show the findings without posting; `--mode <mode>`, the review's depth (default `ticket`); `--base <ref>`, what the change is reviewed against (default `origin/<the PR's base branch>`; for `hub`, the ticket's own base, since the PR's base is the ticket branch; for `re-review`, the head last reviewed); `--run <run>`, a `build-epic` run folder, whose `decisions.md`, `ci:` line and `map.md` Checks the reviewers read; `--decisions <path>`, the run's decisions file (a `build-epic` run's `decisions.md`: which of the repo's leave-for-human rules the human waived, and their verbatim decisions), when it is not `<run>/decisions.md` or there is no `--run`; and the files a mode needs, below.

**Modes**, each rendered into the reviewer's prompt by `review_prompt.py` (step 3):

| Mode | Reviews | Reviewer | Needs |
|---|---|---|---|
| `task` | one task PR, against its base; with no PR, a task's own commits before they merge (build-epic's high-tier tasks, reviewed here, never remotely) | PR | `--task <file>` optional; required with no `--pr` |
| `hub` | A: the hub task PR against `--task-base` (the ticket branch); B: the whole ticket against the base, in one run | PR | `--ticket <file>`, `--task-base <ref>`, `--task <file>` optional |
| `ticket` | the whole PR, once and in depth | PR | `--task <file>` optional (the ticket file) |
| `re-review` | only the diff since the head last reviewed (`--base`), checking a numbered list of earlier findings | PR | `--findings <file>` |
| `security` | the PR for security, beside a `hub` or `ticket` review of a high-tier change | security | none |

## Steps

1. **Learn the rules** ([how](../_shared/conventions.md#learn-the-rules); notes file `.agents/review-pr-notes.md`). Done when you know which files hold the repo's rules and which identity to post as.

2. **Check out the PR head** in its own git worktree: `git fetch origin pull/<n>/head && git worktree add --detach <path> FETCH_HEAD`. Done when the worktree's HEAD matches `gh pr view <n> --json headRefOid`.

3. **Start the reviewers**, each a subagent with a fresh context, in parallel. Each saves its report in `<run>/reviews/`, `<run>` the `--run` folder. Without `--run`, make a scratch one for the reports and the posting log: `python3 -I ~/.agents/skills/build-epic/scripts/init_run.py <new empty folder> <repo>` (`OK run initialised ...`); pass it to the scripts below as `<run>`, but never as `--run` to `review_prompt.py`, since it holds no `decisions.md` or `map.md`.
   - **Tier the change**, in `hub` and `ticket` modes: `python3 -I ~/.agents/skills/review-pr/scripts/tier.py --git <worktree> $(git -C <worktree> merge-base <base> HEAD)`, `<base>` the `--base` ref. Its first line is the **risk tier**, `low` or `high`; the lines under it are the signals that decided it. (`tier.py --trim <diff file>` cuts a diff to its changed files and added lines: that is how the fixtures under `scripts/fixtures/` were made from the gh-35 PRs.)
   - **Render each prompt**: `python3 -I ~/.agents/skills/review-pr/scripts/review_prompt.py <mode> --pr <n> --worktree <worktree> --head <head sha> --base <ref> [--run <run>] [--decisions <path>] [--task <file>] [--ticket <file> --task-base <ref>] [--findings <file>] --report <run>/reviews/<n>-<sha7>.md`, with the options its mode needs (Modes above; `hub` refuses to run without `--ticket` and `--task-base`, `re-review` without `--findings`). `--base` is the `--base` ref above. Write its output to a file and give that output, as printed, as the reviewer's whole message: it points at the brief, the diff and the run's files (the brief has the reviewer find the repo's rule files itself), and holds no opinion of the PR or summary of it, so the reviewer's read is not anchored on yours. `--report` names the reviewer's report file, `<sha7>` the head's first 7 characters, and the security reviewer's ends `-security.md`; the prompt makes it the one file the reviewer may write. Never write or add to a prompt yourself.
   - **PR reviewer**, always, in the mode given (the `pr-reviewer` agent if your harness defines one, otherwise a general-purpose subagent told to follow [reviewer-brief.md](reviewer-brief.md)).
   - **Security reviewer**, only in `hub` and `ticket` modes, and only when the tier is `high`: the `security` mode's prompt (`--base` as for the PR reviewer), to the security reviewer agent if your harness defines one, otherwise a general-purpose subagent told to follow [security-brief.md](../security-audit/security-brief.md). A `low` tier gets none, whatever the files are; a `task` or `re-review` run never gets one, since its ticket's deep review decides.

   - **Remotely**: a reviewer runs on the remote backend when [Remote subagents](../remote-subagents/SKILL.md) lets its agent run there (its declaration, `remote-agent ready`, no `--local`) and the PR's author is the human or the run's identity (a `build-epic` run's task, hub and ticket PRs); otherwise it runs here as above, and nothing below changes. The remote sandbox holds a token and reaches the network, and the reviewer runs the PR's tests there, so a PR by anyone else (its `conftest.py`, say) could send the token out: review it here, reading the whole diff before running anything. Render its prompt as above, but with `--remote <dir>` in place of `--report`, and one `--allow-author <login>` for the human's login (`gh api user --jq .login`) and one for the identity you post as (step 1), as `gh pr view <n> --json author` spells them (an App's as `app/<its slug>`), `<dir>` a new empty folder (`<run>/reviews/<n>-<sha7>-remote/`, `-security-remote/` for the security reviewer). It writes the diff (both diffs in `hub` mode) and the PR facts into `<dir>`, lists the files to attach in `<dir>/attach.txt` (those, the decisions file, `map.md`, `spec.md`, the task or ticket file and the findings), and prints a prompt naming only `~/work` and `~/attached/<name>`, with no `gh`, no git history and no report file: the reviewer's final message is its report. When it exits 1 (its stderr says why: `author` for a PR by anyone else, `pr-view`, `diff` or a missing input), run that reviewer here instead. Start it with `~/.agents/bin/remote-agent --name review-<n>-<sha7> --attach <each line of attach.txt>... @<prompt file> <worktree>` (`security-<n>-<sha7>` for the security reviewer), as that skill's steps say. When it ends, copy the run's `report_path` from `remote-agent result <name>`, unchanged, to the report file `--report` would have named (`<run>/reviews/<n>-<sha7>.md`): that copy is the report file of steps 4 and 5, posted here, byte for byte from the saved summary. A reviewer changes nothing, so it exits 3; on exit 0 it left changes in the worktree: never commit them, step 6 discards them. Any other exit, or an empty report, falls back to a local reviewer.

   Start each reviewer with a description (the short label your harness shows and saves, where it has one) beginning with its role, as [build-epic](../build-epic/SKILL.md#subagents) lists them, so telemetry files its cost by role: `review: PR <n>` (`task` and `hub`), `ticket-review: PR <n>`, `re-review: PR <n>` and `security: PR <n>`. Without `--run` or `--decisions`, the prompts name no decisions file, and the briefs apply every rule as written. If your harness has no subagents, follow each prompt and its brief yourself in turn, before reading anything else about the PR. Done when every reviewer started has returned its block (a remote one, its report) and its report file exists.

4. **Verify.** Read each report file. For each finding, open the code it cites and confirm the failure scenario really happens: trace the inputs, or run the code or a test. Mark what does not hold **dropped**, and what you could not settle **plausible**; never edit a report. Done when every finding is **confirmed**, **plausible** or **dropped**.

5. **Post** each report as its own review, as the identity from step 1: `python3 -I ~/.agents/skills/build-epic/scripts/post_review.py <run> <n> <report-file> [--base <ref>] [--note <text>]`, `--base` the base the reviewer's diff started from (for a `re-review`, the head it reviewed before). It posts one `COMMENT` review on the head commit (never an approval) whose body is a one-line header (the PR and head reviewed, from the report's name `<PR>-<sha7>`; the PR posted on, when it differs; the diff read, only with `--base`; and the run's `test_command:` from `decisions.md`), the report's bytes unchanged, then the note. The note is your verification from step 4: each dropped finding with its `path:line` and why it does not hold, and each plausible one; with every finding confirmed, leave it out. There are no inline comments: findings cite `path:line` in the report. The posted body is saved beside the report as `<report-stem>.posted<ext>`. It prints `OK PR<n> review <url>`, or `FAIL PR<n> <reason> (log: ...)`:
   - `empty-review`: the report file is missing or blank. Continue the reviewer once (or start a new one), asking it to save its report there.
   - `bad-report`: the report is not UTF-8. Ask the reviewer to save it again in UTF-8.
   - `post-denied <report-file>`: GitHub refused the review. Do not retry: the findings stay in that file, and your report names its path. The same when your harness denies running `post_review.py`.
   - `pr-view` or `post`: the log says why; run it again once.

   With `--dry-run`, show each report and its note instead of posting. Done when each review URL exists, or the reports are shown.

6. **Clean up**: `git worktree remove <path>` (`--force` when a remote reviewer left changes in it).

## Report

Each review URL (or, with `--dry-run`, the report paths) and the confirmed and plausible findings, most severe first, one line each. When posting was denied, the report path from the `post-denied` line.
