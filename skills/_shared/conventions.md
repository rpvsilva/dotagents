# Shared conventions

Steps several skills share. A skill links to the section it needs; follow that section as if the skill held it.

## Learn the rules

Run `~/.agents/bin/settings list <skill>` in the repo: the skill's **Settings**, one per line as `<skill>.<key> TAB <value> TAB <Level> TAB <meaning>`, already resolved across flag, repo, machine and default. Use them as they are; never read a settings file yourself. When it fails, relay its message and stop. Then read, if they exist: the skill's notes file (its Lessons inform your judgement), the repo's `AGENTS.md` (or `CLAUDE.md`), `CONTRIBUTING.md` and the PR template (`.github/pull_request_template.md`). A notes line stating a value the skill declares as a Setting is left over from before Settings existed: the Setting wins, and you tell the human that [configure](../configure/SKILL.md) can move the line. Note the **identity** for GitHub and tracker calls (e.g. a `GH_TOKEN` prefix for a bot account); with none named, use the current login. If the rules name a setup that is missing, stop and ask the human. Then note what the skill's step lists.

## Subagents

Start the named agent if your harness defines it, otherwise a general-purpose subagent told to follow the brief. Hand over the inputs the brief lists as **paths**, never summaries, so its read is not anchored on yours: the prompt is the brief's path, then one `<input>: <path>` line per input (the task, the run folder, the worktree, the report file), and never restates what those files hold. If your harness has no subagents, follow each brief yourself, one at a time, writing the same files.

At most **N** subagents run at once on this machine (the **slots**): `--parallel N`, else the skill's `max_parallel` Setting. [Remote subagents](#remote-subagents) take **remote slots** instead, counted apart: at most `~/.agents/bin/settings get remote max_sandboxes` at once, whatever the skill. When a skill says "while a slot is free", it means a slot of the kind the subagent will use, so a run with remote on can have N local and the remote slots' worth of subagents going at once. Slots are a **ceiling**, never a target: start a subagent when its work is ready and separable from what is running. Every run spends the account's usage quota, so the work sizes a burst.

Run your own git commands on a shared repo one at a time (`fetch`, `worktree add` and `remove`, `branch -D`, `push`): git locks its refs and config, so two at once fail.

### Reports

When the prompt names a **report file** (a skill with a run folder names `<run>/reports/<id>.md`), the subagent first writes its full report there, ending with its block, and then its final message is only the **block**: the lines `status:`, `changed:`, `why:` and `follow-up:`, in that order (empty values allowed), at most 400 characters, optionally inside one code fence. A longer or other-shaped message is a brief violation. With no report file named, the final message is the full report, ending with the block. Whoever started it reads the block alone and opens the report file only on `blocked` or `plan-wrong`, or when the skill's next step reads it (a review's findings, a tuner's mutations). In a `build-epic` run, check each block with `python3 -I ~/.agents/skills/build-epic/scripts/report_check.py <run> <id>`, the block on its stdin: `FAIL <id> brief-violation ...` means the subagent broke its brief; continue it once (or start a new one on the same worktree) asking for the report file and the block, and on a second violation act as on `blocked`, with that line as the `why`. A remote subagent cannot reach the run folder: see [Remote subagents](#remote-subagents) step 3.

## Remote subagents

A subagent the skill marks **remote-capable** (it only changes its worktree) runs on the remote backend (the `remote.backend` Setting: a cluster, Docker or an SSH host) instead of this machine when `~/.agents/bin/remote-agent ready` exits 0 in the repo and the human did not ask for `--local`. `ready` prints the backend, or why remote runs are off: no backend set, no token, the repo sets `remote.allowed` to `false`, or the backend does not answer (with its error). Say that reason once, then run subagents locally. The backend is compute only: it gets this machine's setup, a snapshot of the worktree and the files you attach, and gives back a patch. It has no GitHub access and no git branches, so it cannot push, open a PR, read CI logs or see another branch. Details: [remote/README.md](../../remote/README.md). The human sets it up with `~/.agents/bin/remote-agent setup` and proves it with `remote-agent check`. When the human asks to turn remote off or change it, follow [configure](../configure/SKILL.md).

1. Create the worktree as for a local subagent.
2. Write the message you would hand the subagent into a file. Name the worktree as `~/work`, and every other input as `~/attached/<its file or folder name>`. Attach only what its brief reads, never a whole run folder holding other worktrees.
3. Run `remote-agent --name <task> --attach <path>... @<message file> <worktree>` in the background, with a short task name the skill gives (e.g. a build-epic task's `TT-NN-<slug>`). `remote-agent` is `~/.agents/bin/remote-agent`. It takes a remote slot, not a local one. Its stdout is the subagent's report, printed once: its full report, ending with the block as its last four lines, unfenced. When the skill names a report file for it, send stdout there (`> <report file>`; stdout only) and read the block at the file's end, from its last `status:` line (in a `build-epic` run, `report_check.py <run> <id> --from-report` checks it there); otherwise read the report from stdout alone. Its stderr is progress, one line per step, each starting with `[<task>]`.
   - Do not redirect its stderr: no `2>file`, no `2>&1 | <filter>`, no `2>/dev/null`. Left alone, each progress line shows to the human as it arrives; a run that only shows its result at the end looks like no agent is attached.
   - When the run starts, give the human the transcript path from its `transcript:` line on stderr. That file holds the subagent's full event stream as it arrives; beside it, `run.json` says the run's state and timings and `progress.log` holds its progress lines.
   - If your harness cannot show a background command's output while it runs, give the human the transcript path and read the run's stderr between other work.
   - The run keeps the remote subagent's session but does not place it for `/resume`: the sandbox wrote it, so it may hold forged turns that read as the human's. Never place it yourself. If the human wants to resume it, give them the `remote-agent resume <run> <worktree>` command from the run's `session:` line on stderr; it warns before placing.
4. Act on the exit code:
   - **0**: the changes are in the worktree, uncommitted. Commit them as the subagent would have, with the repo's commit convention, then act on the report.
   - **3**: no changes; act on the report.
   - **4**: the worktree changed after the snapshot; run it again.
   - **5**: the account hit its usage limit, so every remote run will fail the same way until it resets. Hold every new remote run, let the running ones end, and tell the human the reset time from stderr. The task that hit the limit waits with the held ones. Resume once that time has passed, or sooner when the human switches the account.
   - **Anything else**: treat it as `blocked`, with the last lines of stderr as the reason. When two runs in a row fail the same way within a minute, the backend is down: hold every new remote run until `remote-agent ready` exits 0 again.
